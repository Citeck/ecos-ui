# Lexical: картинки комментария перекачиваются на каждое нажатие клавиши (COREDEV-380)

## Проблема

Пока пользователь набирает комментарий, в который вставлена картинка, каждое нажатие клавиши
порождает новый HTTP-запрос `…/webapp/content?ref=attachment%40…` за каждой картинкой комментария.
В DevTools это десятки ответов 200 по ~13 KB, инициатор — `ImageNode.tsx:130` (в версии 2.29.x это
строка `element.setAttribute('src', …)` в `exportDOM`).

Воспроизведение на локальном стенде (`/v2/dashboard?ws=TEST&recordRef=emodel/ept-issue@TEST-1`,
комментарий → вставить картинку из буфера → набрать 10 символов): 10 запросов за картинкой.

## Корневая причина

Гипотезы из задачи (кеш `imageCache` в `ImageComponent`, ре-рендер `LazyImage`) ни при чём — `<img>`
в редакторе не размонтируется и ничего не перезапрашивает. Запросы делает **сериализация**:

1. `Comment.jsx#handleEditorStateChange` на каждое изменение редактора вызывает
   `$generateHtmlFromNodes(editor)` и кладёт html в state. Так же ведут себя formio-textarea
   (`TextArea.jsx`), HTML-виджет, описание в гантте, `useSyncWithInputHtml` — экспорт в html на
   каждое изменение здесь норма, а не ошибка одного виджета.
2. `ImageNode.exportDOM` строит для этого настоящий `document.createElement('img')` и ставит ему
   `src`. Браузер начинает качать картинку в момент установки `src`, **независимо от того, в
   документе ли элемент** (так работает `new Image().src = …`).
3. Сервис контента отвечает `cache-control: private, no-cache` и не отдаёт 304 на условный запрос,
   поэтому каждый новый `<img>` с тем же URL — полная перекачка.

## Исправление

`src/components/editors/Lexical/nodes/ImageNode.tsx`, `exportDOM`: перед `src` элементу ставится
`loading="lazy"`. По спецификации ленивая картинка не загружается, пока не окажется в документе
рядом с viewport — элемент, который существует только ради `innerHTML`, туда не попадает никогда.
Порядок атрибутов важен: если `src` поставить раньше, загрузка уже стартовала (проверено:
`src` → `loading` даёт запрос, `loading` → `src` не даёт).

Проверено в Chromium через dev-сервер: после правки те же 10 символов — 0 запросов, картинка в
редакторе и в сохранённом комментарии отрисовывается (`naturalWidth` 120). В Firefox (playwright
firefox-1495) отсоединённый `<img loading="lazy" src>` тоже не делает запроса, а вставленный на
страницу — грузится. WebKit не проверен: на машине нет системных зависимостей для его запуска.

Атрибут в хранимый html не попадает: бэкенд санитизирует текст комментария и `loading` вырезает
(в `emodel/comment.text` после сохранения атрибута нет). Импорт (`convertImageElement`) читает
только `alt/src/width/height`, так что и без санитизации ничего не меняется.

Тест `src/components/editors/Lexical/nodes/__tests__/imageExportNoFetch.test.tsx`: `innerHTML`
сохраняет порядок установки атрибутов, поэтому по разметке видно, что `loading` стоит раньше
`src`; плюс проверка, что src/alt/width/height экспортируются как раньше и что свой же html
импортируется обратно в `ImageNode` с тем же `src`.

## Сериализация на каждое нажатие убрана из `Comment.jsx`

`handleEditorStateChange` раньше на каждое изменение оборачивал работу в `editor.update`, гнал
`$generateHtmlFromNodes` по всему документу и делал `JSON.stringify(editorState)`, складывая всё в
state. Этот html/raw из state использовался только как запасной вариант в `getContentToSave`, когда
`this._editor` не назначен — а `onEditorReady` назначает его при монтировании, раньше любого ввода.
То есть на каждое нажатие выполнялась работа, результат которой никогда не читался.

Теперь обработчик считает только два флага для подвала: `isMaxLength` (по
`$getRoot().getTextContentSize()` документа — так же, как считает лимит сам `Editor`; раньше брался
`textContent` DOM-корня, который короче на переносы между абзацами) и `isEditorEmpty` (приходит из
`Editor`). Текст для отправки по-прежнему строится из живого редактора в `getContentToSave`.

### Редактор без `onEditorReady` (плагин активностей)

`Activity.jsx` в плагине активностей наследует `Comment`, но передавал редактору только `onChange`:
`this._editor` в нём никогда не назначался, и активность сохранялась через запасной html/raw из
state. С его удалением она ушла бы на сервер пустой (нашло ревью). Три вещи закрывают это:

- `handleEditorStateChange` сам запоминает редактор, который передаёт `OnChangePlugin` — базовому
  классу достаточно одного `onChange`, если автор хоть что-то набрал.
- Если редактор так и не объявился (`OnChangePlugin` пропускает загрузку `htmlString` — у него
  guard `prevEditorState.isEmpty()`, а `Activity` даёт сохранить запись, изменив только тему или
  дату: `noChanges` там никогда не выставляется), `getContentToSave` возвращает сохранённый текст
  записи (`props.comment.text`) как есть, для обоих форматов. Автор документ не трогал — что
  лежало, то и остаётся; пустая строка здесь стёрла бы текст существующей активности.
- `handleCloseEditor` обнуляет `this._editor`: `Activity` существующей записи не размонтируется
  между сеансами редактирования, и закрытый (возможно, с отменёнными правками) редактор не должен
  отдавать свой документ следующему сохранению.

Плюс в самом плагине (`ecos-ui-activities-widget-plugin`, релиз 1.6.6 на master, тег `1.6.6`)
редактору подключён `onEditorReady={this.handleEditorReady}`, как в `Comment.jsx` — тогда и
активность, открытая на редактирование без набора текста, сохраняется из живого редактора с
подрезкой краёв. В `ecos-build-config.yml` ecos-ui плагин поднят до `activities-widget:1.6.6`.

Попутно убраны мёртвые ключи state: `htmlString` в `handleCloseEditor` и `htmlComment`/`rawComment`
в `Comments.jsx` — их никто не читал.

`Comments.jsx` теперь передаёт `dataStorageFormat` в оба `<Comment>` (ревью заметило, что проп
объявлен, реестр виджетов задаёт `html`, но до `Comment` он не доходил и всегда работала ветка по
умолчанию). Для `html` это ничего не меняет в хранимом тексте: замена `<br>\n` → `<br/>` в этой ветке
осталась от прежнего редактора, Lexical переводов строки после `<br>` не экспортирует. Реестр
активностей формат не задаёт, плагин не трогали.

Остальные места с экспортом на каждое изменение — formio-textarea, `MLLexicalEditor`,
`useSyncWithInputHtml`, гантт (с дебаунсом) — отдают значение наружу по контракту компонента, там
экспорт нужен; от перекачки картинок их защищает правка в `exportDOM`.

Тест `CommentSave.test.js`: `$generateHtmlFromNodes` подменён спаем — на изменение он не вызывается,
в state не попадают `htmlComment`/`rawComment`, флаг лимита считается по документу (4999 — нет,
5000 — да); редактор, пришедший через `onChange`, достаточен для сохранения; без редактора
`handleTextBeforeSave` возвращает сохранённый текст записи (или `''` для новой); после
`handleCloseEditor` редактор забыт и сохранение снова отдаёт сохранённый текст.

Проверено на стенде: набор текста с картинкой — 0 запросов за контентом, кнопка «Отправить»
выключается на пустом редакторе и включается после Ctrl+Z, сохранённый комментарий содержит текст
и картинку.
