# Select: поиск показывает не то, что введено (COREDEV-359, переоткрытие)

После снятия лимита в четыре совпадения ([select-search-results-limit.md](./select-search-results-limit.md))
QA переоткрыла задачу: поиск в `EcosSelect` оставляет в списке значения, не содержащие введённый
текст. На списке версий ввод `2026.2.1` оставлял `2026.1.1`, `2026.4.1` и `2026.5.1` — все три
значения, которые пользователь как раз отфильтровывал; ввод `2025.13` оставлял `2025.12`,
`2025.1.5`, `UI 2025.1.4`. Ожидание: в списке остаётся только то, что буквально содержит введённую
строку; нет таких значений — список пуст.

## Корневая причина

choices.js 8.0.0 ищет через fuse.js 3.6.1 — нечёткий (bitap) матчер. `EcosSelect` и переопределённый
formio `select` передают ему `threshold: 0.3` (formio-вский `searchThreshold` по умолчанию;
он сохранён в определениях существующих форм, так что смена дефолта в схеме компонента ничего не
чинит). С порогом 0.3 строки, отличающиеся одной цифрой, проходят как совпадения — это и есть
«несвязанные значения» на скриншотах. Подбором порога префиксную/подстрочную семантику из fuse 3
получить нельзя: оценка зависит от длины строки и позиции совпадения, а не от «содержит/не содержит».

Затронут только клиентский поиск (`searchChoices: !searchField`): когда у компонента задан
`searchField`, choices.js сам не фильтрует, а компонент шлёт `__regex`-запрос на сервер.

## Исправление

В общем модуле `src/forms/choices/index.js` (через него библиотеку импортируют оба компонента)
переопределён `Choices.prototype._searchChoices`: вместо fuse — буквальный регистронезависимый
поиск подстроки по настроенным `searchFields` (по умолчанию `label` и `value`).

- Совпадения ранжируются позицией вхождения: значение, начинающееся с введённого текста, выше
  значения с вхождением в середине (`score` = индекс вхождения, сортировка choices.js по
  возрастанию оценки сохранена).
- Ярлыки приходят в виджет уже прогнанными через шаблон компонента, то есть с разметкой — ищем по
  видимому тексту (`innerText` отсоединённого контейнера), а не по тегам: `span` больше не находит
  весь список.
- Значения не всегда строки (`EcosSelect` держит объекты в `value`) — нестроковое поле просто не
  участвует в поиске.
- Формат результата (`[{ item, score }]`) и диспатч `FILTER_CHOICES` повторяют оригинал, так что
  редьюсер и отрисовка библиотеки не тронуты.

`fuseOptions`/`searchThreshold` в конфиге компонентов остаются (их прокидывание покрыто спеками
`EcosSelect.spec.js` / `Select.spec.js`), но на клиентскую фильтрацию больше не влияют.

## Проверка

- `src/forms/choices/__tests__/search.spec.js` — сценарии из переоткрытия: `2026` находит все три
  версии, `2026.2` и `2026.2.1` — пусто; `2025.12` оставляет `2025.12` и `UI 2025.12`, отбрасывая
  `2025.1.5` и `2025.13`; регистронезависимость; ранжирование префикса выше середины; поиск по
  тексту ярлыка, а не по разметке; объектные значения не роняют поиск.
- Браузер (дев-сервер, журнал `ui-actions` → «Edit Properties» → поле «Action Type», 27 опций):
  опечатка `crate` → «No results found» (раньше fuse оставлял `Create`); `creat` → только `Create`.
  Пустого места под списком нет — исправление первой половины тикета продолжает работать.

## Замечания по инструментам

- Поиск choices.js слушает `keyup` на своём инпуте: Playwright-овский `fill()` фильтрацию не
  запускает, нужен `pressSequentially()`.
