# Lexical: Ctrl+Z «периодически» не работает после Ctrl+V и после «Вставка» (COREDEV-454)

## Проблема

В комментарии на Lexical-редакторе отмена (Ctrl+Z) «периодически» не срабатывает: после вставки
текста через Ctrl+V и после добавления элемента через меню «Вставка». Обычный набор текста при этом
отменяется. Воспроизводится нестабильно — у одного человека есть, у другого «вроде работает».

## Корневая причина: раскладка клавиатуры

Lexical 0.26 распознаёт undo/redo **только по символу** клавиши:

```js
// node_modules/lexical/Lexical.dev.mjs
function isUndo(key, shiftKey, metaKey, ctrlKey) {
  return key.toLowerCase() === 'z' && !shiftKey && controlOrMeta(metaKey, ctrlKey);
}
```

На русской раскладке Ctrl+Z приходит как `key: 'я'`, `code: 'KeyZ'` — `isUndo` не срабатывает,
`preventDefault()` не вызывается, и нажатие уходит браузеру. У браузера есть **свой** undo для
`contenteditable`: он шлёт `beforeinput` с `inputType: historyUndo`, и Lexical его ловит (`case
'historyUndo'` → `UNDO_COMMAND`). Но браузер шлёт его только когда в его **нативном** стеке есть
запись. Набор текста такую запись оставляет; вставка (Lexical перехватывает `paste` и вставляет
программно) и узлы из меню «Вставка» — нет. Отсюда картина: «после набора отменяется, после Ctrl+V
и после «Вставка» — нет», и «плавает» между людьми — зависит от раскладки в момент нажатия.

Проверка на локальном стенде (комментарий, Chromium): синтетический `keydown` с `key: 'я', code:
'KeyZ', ctrlKey` после вставки — текст на месте; тот же keydown с `key: 'z'` — вставка отменена. То
же после обычного набора: с `я` Lexical ничего не делает (нативный путь синтетикой не воспроизвести).

Что **не** подтвердилось (проверено там же): фокус после «Вставка» — и после «Разделитель», и после
модалки таблицы `document.activeElement` остаётся `contenteditable`, Ctrl+Z (латиница) отменяет;
лишние записи истории от `useSyncWithInputHtml` / `updateEditorContent` — после paste и вставки узла
до исходного состояния ровно один Ctrl+Z; шорткаты приложения — Ctrl+Z нигде не перехватывается.

## Исправление

`plugins/ShortcutsPlugin/shortcuts.ts`: предикаты `isUndo(event)` / `isRedo(event)` **по `code`**
(`KeyZ`, `KeyY`, Shift, Ctrl/⌘ как у Lexical, Alt исключён — AltGr на Windows приходит как Ctrl+Alt),
как и все остальные предикаты этого файла. `plugins/ShortcutsPlugin/index.tsx` — первая ветка
обработчика `KEY_MODIFIER_COMMAND`: `preventDefault()` + `UNDO_COMMAND` / `REDO_COMMAND`.

Тонкость: `KEY_MODIFIER_COMMAND` Lexical диспатчит **после** своей цепочки `isUndo/isRedo`, и для
латинской `z` тоже. Поэтому предикаты возвращают `false`, когда `key` — та самая латинская буква
(`z` / `y`): её Lexical уже отменил, второй `UNDO_COMMAND` откатил бы два шага. Тест на это есть.

То же сделано для **Ctrl+B / Ctrl+I / Ctrl+U** (`isBold` / `isItalic` / `isUnderline`, коды `KeyB` /
`KeyI` / `KeyU`, Shift не проверяется — как у Lexical'овского `isBold`): у Lexical они распознаются
по `key` точно так же и на русской раскладке (и / ш / г) молчали. Та же защита от латинской буквы:
второй `FORMAT_TEXT_COMMAND` на одно нажатие снял бы формат обратно. Ctrl+K (ссылка) и все
остальные шорткаты файла и так были по `code`.

## Проверка

- `plugins/ShortcutsPlugin/__tests__/undoRedoLayout.test.tsx` — `LexicalComposer` + `RichTextPlugin`
  - `ShortcutsPlugin`, `keydown` диспатчится на корневой элемент редактора (тот же путь, что у
    реального нажатия, Lexical'овский обработчик идёт первым): Ctrl+я → один `UNDO_COMMAND`,
    `defaultPrevented`; Ctrl+z → ровно один (не два); Ctrl+Shift+я и Ctrl+н → один `REDO_COMMAND`;
    Ctrl+Y / Ctrl+Shift+Z → ровно один; голая `я`, Ctrl+Alt+я, Shift+я — ничего.
- Браузер (локальный стенд, комментарий): синтетический Ctrl+я после Ctrl+V отменяет вставку,
  Ctrl+Shift+я возвращает; после набора — отменяет; после «Вставка → Разделитель» и «Вставка →
  Таблица» без клика в редактор — отменяет; латинский Ctrl+Z после «вставка + набор» откатывает
  ровно один шаг. Форматирование: на выделенном слове синтетические Ctrl+и / Ctrl+ш / Ctrl+г дают
  `<strong>` / `<em>` / `span.rt-editor-theme__text_underline` (подчёркивание у Lexical — класс,
  не `<u>`), второе нажатие снимает; реальный латинский Ctrl+B — одно переключение на нажатие
  (вкл → выкл → вкл), то есть двойного срабатывания нет.

# Второй круг: Ctrl+Z после вставки изображения (COREDEV-454, возврат из тестирования)

## Проблема

Тестирование подтвердило, что с текстом горячие клавиши работают на любой раскладке, но осталось:
скриншот из буфера обмена вставляется через Ctrl+V, а Ctrl+Z «зависает» — изображение остаётся на
месте, поверх него бесконечно крутится лоадер, состояние не меняется.

## Корневая причина: докачка изображения была отдельным шагом истории

Вставленная картинка попадает в документ мгновенно: `DragDropPastePlugin` читает файл в base64 и
диспатчит `INSERT_IMAGE_COMMAND`, а `ImageNode` хранит и `src` (data-url), и сам `File`. Наличие
`__file` — единственное условие спиннера в `ImageNode.decorate`. Загрузку доводит
`OnImageUploadPlugin`: получив url, он делал `editor.update(() => { setFile(undefined); setSrc(url) })`
**без тега истории**.

Обычный `editor.update` для `@lexical/history` — это `HISTORY_PUSH`: в стек undo кладётся состояние
«картинка с файлом и data-url». Поэтому первый Ctrl+Z откатывал не вставку, а докачку, и возвращал
именно тот снимок: изображение на месте, `__file` снова заполнен → спиннер снова включён. Заново
загрузку никто не запускал — слушатель мутаций реагировал только на `created`, а тут `updated`.
Отсюда «бесконечный лоадер и невозможно работать дальше».

Второй дефект в том же месте: колбэк писал в **захваченную ссылку** на узел (`imageNode` из
`read()` старого состояния), а не искал узел по ключу. Если отменить вставку, пока загрузка ещё в
воздухе, `getWritable()` падал с `Lexical node does not exist in active editor state` (в приложении
это гасится `onError: console.error`, поэтому и выглядело «ничего не происходит»).

## Исправление

`plugins/OnImageUploadPlugin/index.tsx`:

- все правки узла из асинхронных колбэков идут с тегом **`history-merge`** (`AS_SIDE_EFFECT`) —
  докачка сливается с текущей записью истории и своим шагом отмены не становится. Первый Ctrl+Z
  теперь убирает саму картинку, Ctrl+Y возвращает её уже с загруженным url;
- узел ищется по ключу **внутри** `editor.update`, и правка применяется, только если это всё ещё
  та же картинка с тем же `File` — отмена во время загрузки больше не роняет обновление и не
  воскрешает удалённый узел;
- слушатель мутаций обрабатывает и `updated`: если отмена всё-таки привела к снимку с незавершённой
  загрузкой (например, после вставки успели набрать текст), картинка **дозагружается**, а не висит
  со спиннером;
- одна загрузка на один `File` (`WeakMap<File, Promise<string>>`): undo/redo носят на узле тот же
  самый объект файла, так что повтор не создаёт второе вложение — при Ctrl+Y картинка возвращается
  с тем же url, POST на `.../webapp/content` ровно один. **Неудачная** загрузка из кеша забывается:
  если отмена возвращает картинку, чей upload упал, она загружается заново, а не выбрасывается по
  старому отказу;
- карта «уже дозагружаемых» узлов живёт на редакторе (`WeakMap<LexicalEditor, Map<NodeKey, File>>`),
  потому что `onUpload` в `EditorContent` — новая функция на каждый рендер, и слушатель мутаций
  перерегистрируется, встречая существующие картинки как `created`. Без неё каждый рендер во время
  загрузки навешивал бы на тот же промис ещё одну цепочку завершения (preload, update, строка в
  консоли при ошибке);
- ошибка загрузки пишется в `console.error` (раньше глоталась голым `catch`), картинка удаляется —
  как и было;
- **пустой шаг undo после сбоя.** Удаление упавшей картинки сливается (`history-merge`) в запись
  истории, созданную вставкой, и если после вставки ничего не происходило, эта запись становится
  неотличимой от предыдущей: первый Ctrl+Z «отменял» бы в тот же документ и выглядел сломанным.
  Поэтому удаление делается `discrete` (слушатель истории отработал синхронно), после чего плагин
  сравнивает `historyState.current` с вершиной `undoStack` (по `editorState.toJSON()`, без
  выделения) и, если они совпадают и принадлежат этому редактору, снимает пустую запись
  (`collapseNoopHistoryEntry`). Состояние истории берётся из `useSharedHistoryContext()` — того же
  контекста, через который `Editor.tsx` отдаёт его `HistoryPlugin`; без провайдера схлопывание
  пропускается. Если автор успел набрать текст, записи различаются и ничего не снимается: его
  Ctrl+Z попадает на снимок вставки, а картинка в нём загружается заново (см. пункт про кеш).

## Проверка

- `plugins/OnImageUploadPlugin/__tests__/undoAfterImagePaste.test.tsx` (10 тестов): загрузка гасит
  спиннер; Ctrl+Z после загрузки убирает картинку (до правки — оставлял её с `__file`); Ctrl+Y
  возвращает её без второй загрузки; Ctrl+Z во время загрузки убирает картинку и пришедший ответ
  её не воскрешает (до правки — исключение о несуществующем узле); отмена на снимок «в процессе
  загрузки» дозагружает картинку; ответ загрузки для файла, которого на узле уже нет, узел не
  трогает (без проверки `getFile() === file` тест падает); ошибка загрузки и неоткрывшийся url
  убирают картинку; после упавшей вставки первый Ctrl+Z отменяет предыдущую правку, а не пустой
  шаг (без `collapseNoopHistoryEntry` падает); Ctrl+Z на снимок с упавшей картинкой загружает её
  заново (без `uploads.delete` падает). Каждый из трёх новых тестов проверен мутацией.
  Тонкости харнесса: Lexical коммитит апдейт в микрозадаче (нужен `await act`); корневой параграф
  создаётся до регистрации `HistoryPlugin` — без установки каретки после монтирования истории не с
  чего начинать и отменять нечего; история и плагин связаны через `SharedHistoryContext`, как в
  `Editor.tsx`; восстановление состояния с текстовой кареткой заставляет Lexical мерить `Range`
  ради прокрутки, а у jsdom нет `Range.getBoundingClientRect` — он заглушен в `beforeEach`;
  загрузки с управляемым исходом — через `queuedUploads` (по промису на вызов), а не
  `mockRejectedValueOnce`: мгновенный отказ срабатывает ещё до набора текста и меняет сценарий.
- Браузер (локальный стенд, комментарий у `emodel/ept-issue@TEST-1`, реальный `Ctrl+V` из
  `navigator.clipboard`): до правки после Ctrl+Z — 1 картинка, 1 спиннер, `src` снова data-url;
  после правки — 0 картинок, 0 спиннеров, текст до картинки на месте, Ctrl+Y возвращает картинку с
  загруженным url, POST ровно один. То же с задержкой ответа загрузки на 6 с (`page.route`): Ctrl+Z
  во время спиннера убирает картинку, ответ ничего не возвращает, ошибок в консоли нет. То же
  синтетическими Ctrl+я / Ctrl+н (русская раскладка).
