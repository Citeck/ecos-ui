# Отладочный режим ЭП

Подписание документа в UI требует КриптоПро CSP, браузерного плагина, расширения и
сертификата, **закрытый ключ которого создан внутри этого CSP** — импортировать
готовый ГОСТ-ключ снаружи CryptoPro не даёт. На машине разработчика этого обычно нет,
и тогда любой сценарий с подписью не деградирует, а полностью блокируется: пройти
процесс до конца нельзя.

Отладочный режим подменяет **только криптографический примитив** — объект плагина.
Всё, что выше, идёт штатным путём: диалог выбора сертификата, запрос digest'а
(`edi/esign-digest-att-get`), выгрузка подписи (`edi/esign-digital-signature-put`),
обработка ошибок. Поэтому режим годится и для ручной отладки, и для UI-автотестов.

## Включение

Значение конфига `app/edi$esign-dev-mode` (JSON). Конфиг живёт в **ecos-edi**
(`eapps/artifacts/app/config/esign-dev-mode.yml`) — там же, где остальной серверный
контракт ЭП (`edi/esign-digest-att-get`, `edi/esign-digital-signature-put`) и соседние
ручки подписи. По умолчанию режим выключен.

```json
{ "mode": "stub" }
```

```json
{ "mode": "remote", "url": "/gateway/edi-sim/admin/api" }
```

| Поле | Значение |
|---|---|
| `mode` | `off` (по умолчанию) · `stub` · `remote` |
| `url` | база сервиса подписи, только для `remote` |

Конфиг серверный: браузер сам себе режим не включит, значение ставит администратор
стенда. Меняется в рантайме, пересборка не нужна.

## Режимы

**`stub`** — ничего внешнего не требуется. Три синтетических сертификата:
действующий, истёкший и ещё не вступивший в силу (последние два намеренно — такие
состояния тяжело получить от настоящего УЦ, а UI обязан их корректно отрабатывать).
Байты подписи — маркер `ECOS-DEV-SIGNATURE …`, не CMS: сервер сохранит подпись, но
разобрать сертификат из неё не сможет, поэтому атрибуция подписанта и штампы ЭП
останутся пустыми.

**`remote`** — сертификаты и подпись берутся у сервиса подписи по HTTP. Его реализует
[citeck-edi-sim](https://github.com/citeck/citeck-edi-sim): `GET {url}/certificates`
и `POST {url}/certificates/{id}/sign`. Возвращается **настоящий detached CMS** с
настоящим сертификатом (ГОСТ-2012 / RSA / ECDSA), поэтому атрибуция подписанта,
сверка отпечатка и штампы работают так же, как в проде.

`url` ожидается **same-origin** — например путь через gateway, если сервис подписи
зарегистрирован в ECOS. Кросс-доменный адрес потребует CORS на стороне сервиса.

## Что режим не проверяет

Связку «CryptoPro CSP + плагин + расширение → UI». Всё, что ниже объекта плагина,
подменено, поэтому на отладочном режиме нельзя принимать решение о работоспособности
самой криптографии — только о поведении процессов над ней.

Подпись, полученная в этом режиме, **не является доказательством ничего**. Поэтому она
маркирована на всех уровнях: баннер в диалоге выбора сертификата, CN сертификатов
(«ТЕСТОВЫЙ СЕРТИФИКАТ (отладка)» / «(отладка)»), издатель `ECOS Dev Stub` и префикс
`ECOS-DEV-SIGNATURE` в байтах `stub`-подписи.

## Код

- `src/services/asyncCadesPlugin/devStub/` — сам стенд-объект плагина;
- `src/api/esign.js` — ветка в `getCadespluginApi()`;
- `src/services/config/ConfigService.js` — константа `ESIGN_DEV_MODE`;
- `src/components/domain/Esign/EsignModal.jsx` — баннер режима.
