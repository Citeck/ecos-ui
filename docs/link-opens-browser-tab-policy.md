# Куда открывается ссылка: вкладка приложения или вкладка браузера (COREDEV-433, итерация 3)

## Правило

Для любой ссылки в приложении — в ответах ИИ-ассистента, в комментариях, в виджетах:

| ссылка | левый клик | Ctrl / Cmd / Shift + клик, средняя кнопка |
|---|---|---|
| этот хост, тот же воркспейс (или воркспейс не указан) | **вкладка приложения** (`PageTabs`) | вкладка браузера |
| этот хост, **другой воркспейс** (`ws=` отличается) — журнал, дашборд, карточка записи | **вкладка браузера** | вкладка браузера |
| другой хост | вкладка браузера | вкладка браузера |

Ссылка без хоста (`/v2/…`) считается ссылкой на текущий хост. Клик с модификатором и средняя
кнопка всегда открывают ровно одну вкладку браузера — нативно, с `href` ссылки как есть (`ws`
ссылки сохраняется).

Исключений для карточки записи **нет** (итерация 3). В итерации 2 карточка чужого воркспейса
открывалась вкладкой приложения в текущем воркспейсе с подменой `ws` — но дашборд записи
резолвится по воркспейсу, в котором карточка показана (`api/dashboard.js`, `query.workspace`),
и SD-заявка внутри `contracts-workspace` получала чужой дашборд. Решение (Павел, 2026-08-27):
любой чужой `ws` → вкладка браузера, без подмены.

## Где это решается

Единственный маршрутизатор — `PageTabs.handleClickLink` (`src/components/layout/PageTabs/PageTabs.jsx`):
`ClickOutside type="click"` слушает `click` на `document` в фазе захвата, `PageService.parseEvent`
берёт ближайший `a[href]`, выходит для `data-external`, для ссылок внутри `.ecos-modal` и для
адресов без `/v2`, иначе делает `preventDefault()` и отдаёт ссылку. Дальше `handleClickLink`:

- чужой хост → `window.open(link, '_blank')` (было и раньше);
- **свой хост, но `ws` ссылки задан и отличается от `getWorkspaceId()` при включённых воркспейсах →
  `window.open(link, '_blank')`** — новое. Раньше такая ссылка шла in-app с `needUpdateTabs`:
  `sagaSetOneTab` делал `push` адреса с чужим воркспейсом, воркспейс переключался под списком
  вкладок, и `Dashboard` (он ничего не рисует, пока его `tabId` не стал активной вкладкой)
  монтировался с пустой конфигурацией — белая страница из итерации 1;
- иначе → `setTab` (вкладка приложения; ссылка без `ws` дополняется текущим воркспейсом в саге).

Клик с модификатором решается раньше, в `PageService.parseEvent`: при `ctrlKey || metaKey ||
shiftKey` он возвращает `undefined` **до** `preventDefault()`, и `handleClickLink` ничего не
делает — вкладку открывает браузер. Сам `window.open` здесь недопустим: браузер откроет свою
вкладку поверх — две вкладки (та же история, что с `mouseup` у средней кнопки). До итерации 3
`parseEvent` забирал Ctrl+клик под фоновую вкладку приложения (`isActive: false`, код 2020 года),
а Cmd на macOS не распознавал вовсе — Cmd+клик открывал *активную* вкладку приложения. Фоновая
вкладка приложения осталась только за атрибутом `data-open-in-background`.

Программные переходы (`PageService.changeUrlLink` с `needUpdateTabs` — переключение воркспейса,
поиск в шапке, `AssocLink`, действия над записью) идут через `sagas/customEvent.js`, а не через
`handleClickLink`, и не затронуты: они переключают воркспейс намеренно.

Средняя кнопка: браузер не генерирует `click`, обработчик захвата не вызывается, вкладку
открывает нативное действие `auxclick`. Перехватывать это на `mouseup` нельзя — см.
`docs/comment-link-opens-two-tabs.md` (COREDEV-248).

## Ассистент

В итерации 1 все ссылки ответа получали `data-external` + `target="_blank"` — то есть всегда
вкладку браузера. Теперь `ChatMarkdownLink` (ответы, объяснения в `ScriptDiffViewer` и
`AIInlineResult`), `ArtifactsList` и `ContextArtifactsList` рендерят обычные якоря; общий
`externalLinkProps(href)` добавляет `target="_blank" rel="noopener noreferrer"` только для чужого
хоста — без него внешняя ссылка без `/v2` (маршрутизатор её не берёт) увела бы текущую вкладку
браузера из приложения. Ссылка на выборку в журнале больше не исключение: она такой же якорь
своего хоста и переиспользует вкладку журнала через тот же маршрутизатор.

  Тесты `ArtifactsList`/`ContextArtifactsList` приведены к той же политике.
- Браузер (итерация 3, локальный стенд, страница `/v2/dashboard?ws=TEST&recordRef=emodel/ept-issue@TEST-1`,
  Playwright-контекст с `httpCredentials`, счёт `context.waitForEvent('page')` и
  `.page-tab__tabs-item`): карточка чужого ws (`ws=PC-DEFAULT`) обычным кликом → 1 вкладка
  браузера с `ws=PC-DEFAULT`, дашборд отрисован; Ctrl+клик по ней → 1 вкладка браузера; Ctrl+клик
  и Shift+клик по ссылке своего ws → по 1 вкладке браузера, вкладок приложения не прибавилось;
  средняя кнопка → 1 вкладка браузера; обычный клик по своему ws → вкладка приложения, вкладок
  браузера 0. Второй вкладки (дубля) ни в одном случае.

## Известное ограничение: `ws` в ссылке ассистента

Маршрутизатор верит `ws` из `href`. Если ссылка ассистента на запись чужого воркспейса пришла с
воркспейсом **сессии** (`…?ws=contracts-workspace&recordRef=emodel/sd-request-type@SD-197342`),
она выглядит своей: ЛКМ откроет карточку вкладкой приложения в текущем воркспейсе с чужим
дашбордом, средняя кнопка — вкладку браузера с тем же неверным `ws`. Фронт этого не различает
и не должен: на каждый клик пришлось бы грузить `_workspace?localId` записи.

Источник — citeck-ai: `CiteckLinkProvider.getRecordLink(ref, workspaceId)` читает `_workspace.id`
записи только при пустом `workspaceId`, а `QueryRecordsTool.linkWorkspace` (поиск с `ALL` /
`CURRENT` / без аргумента) и `MutateRecordTool` передают воркспейс сессии. Остальные тулы передают
только `ref`, у них ссылка верная. Правка — на стороне ai-сервиса (сначала воркспейс записи, потом
переданный); ecos-ui это не чинит (решение Павла, 2026-08-27).
