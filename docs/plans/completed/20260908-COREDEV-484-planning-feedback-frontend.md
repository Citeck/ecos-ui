# COREDEV-484 (фронт) — честный статус планирования, попытки планировщика, стадии степпера из последнего списка, иконки чипов

Задача: https://citeck.ecos24.ru/v2/dashboard?recordRef=emodel/ept-issue@COREDEV-484 (релиз 2026.3 — уточнено владельцем 2026-09-09, в трекере проставлен «Release 2026.3»).
Парный план бэкенда: `citeck-ai/docs/plans/20260908-COREDEV-484-planning-progress-backend.md`. Контракт полей (раздел 2) в обоих планах одинаковый и является обязательным для обеих сторон.

## Overview

При генерации приложения по спецификации пользователь несколько минут видит одну строку «Составляю план...» (`AgentProgressMessage.jsx`, ветка `agent_planning`) и кнопку «Отменить». Планирование — один тяжёлый вызов модели, который планировщик может отклонить и переспросить до трёх раз; ни фактов анализа, ни номера попытки фронт не показывает. Кроме того, стадии новых видов артефактов (действие, права, доска, карточка записи, настройка журнала, патч, таблица решений) не появляются на ленте степпера, потому что хук фиксирует первый полученный список `availableStages`, а бэкенд добавляет стадии новых видов только после построения плана.

Четыре изменения во фронте:

1. **Факты планирования** — при `agent_planning` под заголовком «Составляю план...» показывать строку из фактов, которые бэкенд уже знает: «ТЗ прочитано · требований: 4 · план: тип данных, форма, процесс, шаблон уведомления». Оценку длительности не показывать.
2. **Попытки планировщика** — при повторной попытке показывать «Попытка 2 из 3: план не покрыл требование «уведомления»».
3. **Стадии степпера из последнего списка** — заменить в `useUniversalChat.js` правило «взять список, если его ещё нет» на «взять список, если он пришёл и отличается от текущего по ключам стадий».
4. **Иконки чипов контекста** — заполнить `CONTEXT_ARTIFACT_ICONS` для всех видов артефактов из реестра бэкенда; для формы взять `fa-wpforms`.

Пункты 3 и 4 не зависят от бэкенда и принимаются сразу. Пункты 1 и 2 отрисовывают поля, которые бэкенд начнёт присылать после выполнения парного плана; до этого фронт при отсутствии полей ведёт себя как раньше (только заголовок).

⚠️ Уточнение по пункту 3 (ревью 2026-09-08): в текущем citeck-ai `buildBusinessAppProgress` (`AgentOrchestratorService.kt`, ~строка 9268) на каждой эмиссии `agent_execution` шлёт полный базовый список `generationStageRegistry.getAllStages()` и явно отфильтровывает стадии новых видов, потому что фронт до этой задачи замыкал первый список; параметр `extraStages` реестра нигде не передаётся. Парный план бэкенда (задача 4: «`availableStages` и стадия — как сейчас») этот пробел не закрывает. Правило «последний список побеждает» — необходимое условие, но живьём случай A1 (стадия «Действие» / «Карточка записи» на ленте) заработает только после того, как бэкенд начнёт передавать в `getAllStages(..., extraStages = <стадии шагов плана>)` и считать процент на той же основе. До этого A1 проверяется через стаб. Это нужно добавить отдельным пунктом в парный план бэкенда.

## 2. Контракт полей прогресса (общий с бэкендом)

Эмиссия `agent_planning` (`GenerationProgress`, camelCase, поля со значением `null` в `businessApp` опускаются):

```json
{
  "type": "agent_planning",
  "progress": 0,
  "message": "Планируем выполнение вашего запроса...",
  "currentAttempt": 2,
  "maxAttempts": 3,
  "retryReason": "план не покрыл требование «уведомления»",
  "businessApp": {
    "stage": "ANALYZING_REQUIREMENTS",
    "progress": 0,
    "availableStages": [{ "key": "...", "label": "...", "icon": "...", "description": "...", "progressRange": { "min": 0, "max": 25 } }],
    "planning": {
      "specRead": true,
      "requirementCount": 4,
      "requestedKinds": ["тип данных", "форма", "процесс", "шаблон уведомления"]
    }
  }
}
```

Правила:

- `currentAttempt`, `maxAttempts`, `retryReason` — на верхнем уровне `GenerationProgress` (первые два поля уже есть в модели, `retryReason` новое). Присылаются на каждой попытке планировщика; `retryReason` — только начиная со второй попытки, короткая русская фраза без завершающей точки, не текст для модели. Для планов без бизнес-приложения тоже присылаются (фронт показывает их в той же ветке `agent_planning`).
- `businessApp.planning` — только для бизнес-приложения. `specRead` — в контексте планирования есть текст документов пользователя; `requirementCount` — число выделенных фактов требований; `requestedKinds` — русские названия видов артефактов, которые план должен содержать (`ArtifactKind.displayNameRu`), в порядке реестра. Числа ожидаемых артефактов и оценки длительности в контракте нет (см. решение ниже).
- Каждая эмиссия `agent_planning` самодостаточна: факты повторяются во всех эмиссиях, а не только в первой. Это остаётся требованием к бэкенду; фронт дополнительно подстрахован от его нарушения (`carryPlanningFields`, см. «Технические детали»), но подстраховка не отменяет требование и не разрешает слать факты только в первой эмиссии.
- Отсутствие любого из полей — допустимое состояние (старый бэкенд): фронт показывает только заголовок.

**Решение об отклонении от текста задачи.** В задаче написано «ожидаемое число артефактов». До построения плана бэкенд знает только виды артефактов, которые запросил пользователь (`RequestedKinds`), а не их число: число типов данных, форм и журналов определяет сам план. Показывать «~8 артефактов» было бы такой же оценкой, как длительность, от показа которой задача отказывается. Поэтому в контракте — перечень видов, а не число. Если владелец задачи всё же хочет число, его можно добавить полем `expectedArtifactCount` позже, не ломая контракт.

`AgentProgressMessage.test.js`:

- планирование без фактов → только заголовок «Составляю план...» (как сейчас, регресс).

- `error: true` → строки фактов и попытки не рисуются, заголовок «Запрос завершился ошибкой» (регресс D-B-7).

`i18nKeys.test.js` — существующие проверки полноты ключей должны остаться зелёными после добавления ключей.

## Technical Details

- `sameStageKeys(prev, next)` (`utils.js`): списки равны, если одинаковой длины и на каждой позиции совпадает `key`; отсутствующий список — пустой. `latestStages(next)` — обновитель для функциональной формы `setGenerationStages`: возвращает `prev` при равных ключах, иначе `next`. Сравнение по `key` (а не по всему объекту): бэкенд шлёт один и тот же список каждые несколько секунд, и одинаковый список не должен становиться новым значением состояния. Примечание: `ChatTabs` не мемоизирован, а `activeBusinessAppProgress` на каждом опросе — новый объект, так что перерисовку ленты это само по себе не убирает; выигрыш — в отсутствии нового массива в состоянии (эффекты и мемоизация потребителей).
- Итоговое сообщение `COMPLETED` (`createAIMessage`): список из него берётся только при пустой ленте (см. ➕ в задаче 1).
- Функциональное обновление `setGenerationStages(prev => ...)` снимает зависимость обработчиков от текущего `generationStages` и убирает устаревшее замыкание — причина, по которой в `useCallback` стояла зависимость `[generationStages]`.
- **Отступление от исходного решения плана (ревью, 2026-09-08, коммит `95dd702f4`).** Изначально план запрещал «запоминать» факты на фронте между опросами: самодостаточность каждой эмиссии — обязанность бэкенда (контракт). В коде это правило смягчено помощником `carryPlanningFields`: если очередная эмиссия того же типа не сообщает о планировании ничего (нет ни одного из четырёх полей `currentAttempt`, `maxAttempts`, `retryReason`, `planning`), группа переносится с предыдущего снимка целиком. Причина — `handlePollingProgress` заменяет агентское `messageData` целиком, и одна эмиссия без этих полей гасила строки фактов и попытки, а следующая возвращала их: заметное мигание под заголовком «Составляю план...». Перенос сделан группой, а не по отдельным полям, чтобы `retryReason` не пережил ту попытку, которую он объясняет.
  - Обязанность бэкенда при этом сохраняется (раздел 2): подстраховка рассчитана на старый бэкенд и на нарушение контракта, а не заменяет его. Парный план `citeck-ai/docs/plans/20260908-COREDEV-484-planning-progress-backend.md` по-прежнему обязан присылать факты в каждой эмиссии.
  - Известное ограничение подстраховки: эмиссия, принёсшая часть группы (например, только счётчики попыток, без `businessApp.planning`), заменяет всю группу и стирает строку фактов. Это осознанный размен в пользу согласованности группы; на текущем бэкенде такая эмиссия не встречается, потому что счётчики попыток он ещё не заполняет.
- Все новые поля необязательные, фронт не падает на старом бэкенде: строки рисуются только при наличии данных.
