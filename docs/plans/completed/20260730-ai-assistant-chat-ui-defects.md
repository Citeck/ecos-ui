# Чат AI-ассистента: гашение устаревших кнопок и три дефекта интерфейса (COREDEV-375)

## Overview

Четыре дефекта интерфейса чата AI-ассистента, найденные прогонами и приёмкой со стороны `citeck-ai`
2026-07-29…2026-07-31. Источник списка — `citeck-ai/docs/plans/20260731-ecos-ui-tasks.md`
(провенанс каждого пункта указан там ссылкой на разделы
`citeck-ai/docs/plans/2026-07-14-engine-b-smoke-observations-testing-plan.md`).
Задача в трекере — [COREDEV-375](https://citeck.ecos24.ru/v2/dashboard?recordRef=emodel/ept-issue@COREDEV-375),
связана с COREDEV-323.

Серверная часть по всем четырём пунктам готова, **изменений контрактов не требуется**.

| Пункт | Дефект | Ценность |
|---|---|---|
| FE-1 | Кнопки прошлых шагов диалога остаются активными и кликабельными | Главный: пользователь может отправить действие для уже разрешённого гейта |
| FE-2 | Подсказка «Подтвердите план…» остаётся под карточкой после отклонения плана | Ложная инструкция в терминированном диалоге |
| FE-3 | Placeholder поля ввода не учитывает движок выбранного агента | Операционному агенту предлагается формулировка конфигурационного сценария |
| FE-4 | Предупреждение React: `disableResize` попадает на DOM-элемент | Шум в консоли, мешает читать настоящие ошибки при приёмке |

FE-1 и FE-2 — один и тот же механизм: сейчас единственный способ погасить кнопки — обнулить
`messageData.actions`, и именно это обнуление открывает дорогу подсказке в `AgentPlanMessage`.
Обе правки делаются одним признаком «действия сообщения больше не актуальны».

**Разобранная причина FE-1.** Кнопки гасятся ровно в одном месте — `useUniversalChat.js:923-928` — и
только у того сообщения, чью кнопку нажали. Диалог при этом продвигается пятью путями, и четыре из
них историю не трогают:

| Путь | Место | Гасит кнопки? |
|---|---|---|
| Клик по кнопке этого же сообщения | `handleActionClick:923` | да |
| Свободнотекстовый ответ | `handleSubmit:652` | нет |
| Приход нового сообщения от сервера | `handlePollingResult:503` | нет |
| Отмена запроса | `cancelRequest:856` | нет |
| Ошибка опроса | `handlePollingError:525` | нет |

**Разобранная причина FE-2.** `AgentPlanMessage.jsx:62`: `{hint && !messageData.actions?.length && …}`.
До клика кнопки есть — подсказка скрыта; после клика `handleActionClick` обнуляет `actions` — подсказка
появляется. Указание «чинить в `BusinessAppMessage.jsx`» в исходном документе неверно: подсказка живёт
в `AgentPlanMessage`.

**Разобранная причина FE-4.** `react-resizable@^3.0.5`, `ResizableBox.js`: список `_excluded` не
содержит `disableResize`, поэтому неизвестный проп попадает в `props` и раскладывается на внутренний
`<div>` (`React.createElement("div", _extends({}, props, …))`). Штатный способ отключить изменение
размера — пустой список `resizeHandles`.

**Ограничение, которое нельзя нарушить.** Комментарий `useUniversalChat.js:917-919` намеренно
поддерживает несколько одновременно живых наборов кнопок: одновременно могут ждать решения несколько
файлов, предложенных к сохранению. Правило «активно только последнее сообщение» без исключения для
действий сохранения файла сломает этот сценарий.

## Development Approach

- **Подход к тестам**: обычный (сначала правка, затем unit-тесты в той же задаче).
- **Подход к FE-1**: вычисление признака на рендере, а не мутация состояния сообщений. Правило живёт в
  одной чистой функции; история сообщений не теряет данные; новый способ добавить сообщение
  автоматически гасит прошлые кнопки, поэтому дефект того же класса не возвращается.
- **Вид неактивных кнопок**: задизейблены (видны, приглушены, некликабельны), а не скрыты — история
  диалога остаётся читаемой и вёрстка не прыгает.
- **Блокировка на время запроса**: пока `isLoading`, кнопки действий неактивны — закрывает окно между
  кликом и ответом сервера, в котором сейчас можно отправить второе действие.
- Полностью завершать задачу перед переходом к следующей; правки мелкие и сфокусированные.
- Обновлять этот файл, если в ходе реализации меняется объём работ.
- Сохранять обратную совместимость: `fileSaveActionTempRef` остаётся экспортированным из
  `useUniversalChat.js` (его импортируют тесты).

## Testing Strategy

- **Unit-тесты**: Jest, каталог `src/components/ai/AIAssistant/__tests__/`. Обязательны в каждой задаче.
- Прогон после каждой задачи: `yarn test:ci src/components/ai/AIAssistant`
  (`test:ci` = `jest --watchAll=false`; `yarn test` — режим наблюдения, для автоматического прогона
  непригоден).
- **E2E-тестов в проекте нет** (Playwright/Cypress не подключены как тестовый фреймворк). Их роль
  выполняет приёмка через Playwright MCP на локальном стенде — обязательный блокирующий шаг перед
  коммитом, вынесен отдельной задачей.
- При каждом прогоне через Playwright проверяются `browser_console_messages` (нет новых JS-ошибок) и
  `browser_network_requests` (нет 4xx/5xx), а также осматривается весь экран на посторонние дефекты:
  сбитая вёрстка, смешанная локализация, «сырые» идентификаторы вместо `?disp`, пустые `null`/`undefined`.

## Technical Details

### Правило актуальности действий

```js
// utils.js
// Actions of a message are stale once the dialog has moved past it: any newer message
// (user reply, progress card, server answer) supersedes the gate the buttons belong to.
// File-save actions are the exception — they are resource-scoped, not dialog-scoped:
// several files may await a decision at once, each valid until its own tempRef resolves.
export const isActionsStale = (messages, index) => {
  const actions = messages?.[index]?.messageData?.actions;
  if (!actions?.length) return false;
  if (messages[index].messageData.actionsResolved) return true;
  if (isFileSaveActionSet(actions)) return false;
  return index < messages.length - 1;
};
```

Почему признак не хранится в состоянии: единственная точка гашения — это то, что и породило FE-1
(четыре пути продвижения диалога её обходят). Правило, выведенное из позиции сообщения, покрывает и
существующие пути, и те, которые появятся позже.

Почему нельзя сопоставлять по `action.id`: идентификаторы `deploy_confirm`, `CONFIRM`, `REJECT`,
`SKIP`, `ABORT` стабильны и повторяются между сообщениями (кнопки эскалации переиспользуют те же
идентификаторы, что и гейт упавшего шага). Ключ — `messageId`, как и отмечено в комментарии
`MessageActions.jsx:45-47`.

### Момент выставления `actionsResolved`

Признак выставляется **после** успешного ответа сервера, как и текущее обнуление `actions`. При
сетевой ошибке кнопки остаются рабочими — это существующее и осознанное поведение, позволяющее
повторить действие. Окно двойного клика между отправкой и ответом закрывается блокировкой по
`isLoading` на уровне `MessageList`, а не переносом записи признака.

### Движок агента и placeholder

`engine` приходит с бэкенда в `GET /api/ai-agent/list` (документированный контракт №1 COREDEV-323,
менять не нужно). `getAgentEngine` уже трактует отсутствие поля как `TOOL_LOOP` — устаревшие агенты
получат операционную формулировку, что верно по смыслу. Значение `selectedAgent` — это элемент списка
агентов целиком (`ChatContextTags.jsx:111` передаёт `agent` как есть), поэтому поле `engine` доступно
без дополнительных запросов.

### Отключение изменения размера окна чата

`ResizableBox` из `react-resizable@3` в `render()` исключает из проброса только известные пропы
(список `_excluded`), а остальные раскладывает на внутренний `<div>`. Поддерживаемые способы отключить
изменение размера — `axis="none"` (маркер остаётся видимым, но перетаскивание ничего не меняет) или
пустой `resizeHandles` (маркер не отрисовывается). Для свёрнутого окна правильнее второе.

### Правки по итогам код-ревью

Ревью нашло три случая, в которых правило из раздела «Правило актуальности действий» вело себя не так,
как задумано. Итоговый код отличается от приведённого выше фрагмента; ниже — что именно изменено и
почему.

**1. Отказ запроса больше не гасит гейт.** Ветка `catch` в `handleActionClick` дописывает в список
клиентское сообщение об ошибке (`isError: true`). По позиционному правилу гейт переставал быть
последним и кнопки отрисовывались заблокированными — прямо вопреки решению из раздела «Момент
выставления `actionsResolved`» («при сетевой ошибке кнопки остаются рабочими»). Проверка позиции
теперь пропускает хвостовые сообщения с `isError`: они сообщают об отказе, а не продвигают диалог.
Неудачная отправка свободного текста сначала осталась не покрытой (гейт перекрывался сообщением
пользователя) — это исправлено правкой 12. При ошибке опроса гейт перекрыт карточкой обработки, и так
и должно быть: запрос до бэкенда дошёл и мог быть применён.

**2. Подсказка гейта без кнопок теперь действительно гаснет.** Условие `isGateLive` из задачи 4
опиралось на `actionsDisabled`, а прежняя реализация правила возвращала `false` для любого сообщения
без действий — то есть ровно для тех, у которых подсказка и отрисовывается. Ранний возврат убран:
актуальность вычисляется для сообщения целиком, а не для его списка действий. Функция переименована в
`isGateStale` — она отвечает не только за кнопки. Случай воспроизводим на терминальной карточке
`FAILED` и на ответе «действие не поддерживается», которые бэкенд отдаёт без кнопок.

**3. Смешанный набор действий больше не запирает файл.** `enrichWithPendingFile`
(`AgentOrchestratorService.kt:893`) дописывает пару «Сохранить/Отменить» нового файла к действиям того
же ответа, поэтому `[CONFIRM, REJECT, new_record|<tempRef>, file_cancel|<tempRef>]` — рабочий вариант.
Проверка `isFileSaveActionSet` требует, чтобы файловыми были **все** действия набора, так что такой
набор считался диалоговым и устаревал целиком, а на следующем ходу со свободным текстом бэкенд эти
кнопки не переотправляет — файл оставался без единого способа его сохранить или отменить. Исключение
перенесено на уровень отдельной кнопки: в устаревшем наборе файловые кнопки остаются рабочими,
остальные блокируются. Заморозка на время запроса исключений не имеет и передаётся отдельным
признаком `actionsFrozen` (`MessageList` → `MessageItem` → компоненты сообщений → `MessageActions`).

**4. Исключение для файловых кнопок действует только до ответа по этому файлу.** Правка 3 сняла с
файловых кнопок блокировку по признаку устаревания целиком — включая уже отвечённые. Признак
`actionsResolved` один на сообщение, а бэкенд дописывает пару «Сохранить/Отменить» на **каждый** новый
файл того же хода (`enrichWithPendingFile`, `newPendings.flatMap`), поэтому одним флагом нельзя
выразить, какое из нескольких решений принято. В результате после сохранения файла его кнопки, как
только запрос завершался и снималась заморозка, снова становились активными — при том что превью из
текста сообщения уже вырезано (`handlePollingResult`), а временный файл на бэкенде удалён. Повторный
клик отправлял действие для несуществующего `tempRef` и заново взводил `pendingFileActionTempRef`.
По сравнению с `develop` это ухудшение: там `actions` обнулялись и кнопки исчезали. Бэкенд на этот
контракт опирается прямо (`AgentOrchestratorService.kt:810-816`: «the frontend clears actions ONLY on
the source message of the clicked action, so the others stay live»).

Решение: клик по файловой кнопке записывает не флаг гейта, а сам ответ по файлу —
`messageData.resolvedFileTempRefs`. `MessageActions` гасит кнопку, чей `tempRef` уже в этом списке,
независимо от `disabled`; остальные файлы сообщения и диалоговый гейт остаются рабочими. Побочно это
исправляет и обратный случай: сохранение файла из смешанного набора больше не помечает решённым
`CONFIRM`/`REJECT`, которых пользователь не касался (после ответа сервера они всё равно устаревают по
позиции, но при ошибке опроса гейт теперь остаётся доступным).

Новые тесты (шесть, сверх списка «Testing Strategy»): в `MessageActions.test.js` — отвечённая
файловая кнопка неактивна, а пара второго файла того же сообщения остаётся рабочей, и то же для
набора, который сам по себе не устарел; в `MessageList.test.js` — оба случая на полном пути отрисовки
(два файла в одном сообщении и смешанный набор); в `useUniversalChatHandlers.test.js` — по одному
`tempRef` на клик при двух файлах в сообщении и отсутствие `actionsResolved` у смешанного набора.
Проверено мутацией: со старым условием `MessageActions` четыре из них падают.

**5. Файловые кнопки гасятся и по достоверному списку живых файлов с бэкенда.** Правки 3 и 4 оставили
единственный способ погасить пару «Сохранить/Отменить» — клик по ней. Но бэкенд удаляет ожидающие файлы
и без клика по этой конкретной паре, а `ChatResponse.pendingFiles` — это как раз полный список живых
файлов диалога (`AgentOrchestratorService.enrichWithPendingFile` и ветка `handlePendingFileSaveAction`,
комментарий на строках 815–816 прямо говорит, что список отдаётся интерфейсу «для гашения кнопок у
удалённых `tempRef`»). Интерфейс его читал только для того, чтобы решить, вырезать ли одно превью
(`handlePollingResult`), а на кнопки не смотрел.

Теперь `handlePollingResult` считает список достоверным по факту его наличия: массив (в том числе
пустой) — это полный набор живых предложений, `null` — «сведений о файлах нет». Все `tempRef`, которых
в достоверном списке нет, дописываются в `resolvedFileTempRefs` каждого сообщения, где они предлагались,
и их превью вырезаются из истории. Ответ без поля не гасит ничего.

Вторая половина правки — в `handleActionClick`: `tempRef` принадлежит диалогу, а не сообщению. При
повторяемой ошибке сохранения бэкенд заново дописывает пары всех выживших файлов к новому сообщению
(`previousTempRefs = emptySet()`), поэтому одна и та же пара может висеть сразу под двумя сообщениями.
Ответ по файлу теперь гасит все её копии, а не только ту, по которой кликнули.

Новые тесты (четыре) в `useUniversalChatHandlers.test.js`: гашение по непришедшему в списке `tempRef`
вместе с вырезанием превью, сохранение кнопок у файла, который в списке есть, отсутствие гашения у
ответа без файловых данных, и гашение обеих копий переотправленной пары.

✅ Остаточный пробел закрыт (второй проход код-ревью). Ранее поле `pendingFiles` приходило только тогда,
когда в ходе появлялось новое предложение файла, поэтому его отсутствие означало сразу две несовместимые
вещи — «живых файлов не осталось» и «ответ вообще не про файлы». Кнопки такого файла оставались
активными, а клик по ним давал ответ «Это предложение уже было закрыто.» Причин было три: свободный

этого ответа удалила ожидающий файл (`enrichWithPendingFile` выходил по `pendings.isEmpty()` /
`newPendings.isEmpty()` до того, как допишет поле). Третий случай был ухудшением по сравнению с
`develop`, где клик по гейту обнулял `actions` всего сообщения и файловая пара исчезала вместе с ними.

Требовавшееся изменение на стороне `citeck-ai` выполнено — коммит `bfc7162` «fix(chat): report the live
file proposals on every response»: `processRequest` стал тонкой обёрткой над прежним телом и штампует
снимок живых предложений на каждом ответе, включая пустой список; `null` остаётся только у ответов,
собранных в обход парадного входа (например, у сообщения об ошибке уровня контроллера), и означает

POST вернул `requestId`, и при последующей ошибке опроса (`handlePollingError`) не снимается — гейт
остаётся погашенным навсегда. Это не ухудшение (в `develop` действия в этот момент обнулялись, кнопки
исчезали) и не противоречит решению из раздела «Момент выставления `actionsResolved`»: оно про сетевую
ошибку **отправки**, когда запрос до бэкенда не дошёл. При ошибке опроса результат действия неизвестен —
оно могло быть применено, и повторная отправка означала бы дублирующее развёртывание. Уточнение к
формулировке правки 1: там сказано, что при ошибке опроса гейт «уже перекрыт карточкой обработки», но
после правки 1 карточка становится `isError` и перестаёт перекрывать — фактически гейт держит
погашенным именно `actionsResolved`. То же относится к `resolvedFileTempRefs`: он записывается сразу
после того, как POST вернул `requestId`, и при ошибке опроса не снимается. Причина та же — результат
неизвестен, файл мог быть уже сохранён, и повторный клик означал бы вторую запись того же файла.

**6. Новая пара «Сохранить/Отменить» гасит свою прежнюю копию.** Правка 5 закрыла обратный случай —
ответ по файлу гасит все копии его пары. Оставалась ситуация, когда копий становится две сразу после
ответа: при повторяемой ошибке сохранения `handlePendingFileSaveAction` вызывает
`enrichWithPendingFile` без списка ранее известных `tempRef` (`previousTempRefs = emptySet()`),
поэтому новое сообщение получает пары **всех** выживших файлов — включая тот, по которому никто не
кликал. Его пара оказывалась активной дважды: под исходным сообщением и под новым. В `develop` такого
не было — клик обнулял `actions` исходного сообщения. Теперь `handlePollingResult` считает пары нового
сообщения единственно актуальными: каждый `tempRef`, который новое сообщение предлагает заново,
дописывается в `resolvedFileTempRefs` всех предыдущих сообщений. Ответы «сохранено» и «отменено»
действий не переотправляют, поэтому их правка не затрагивает. Два новых теста в
`useUniversalChatHandlers.test.js` (переотправленная пара и отсутствие лишнего гашения у обычного
ответа с кнопками гейта); мутацией проверено, что без правки первый из них падает.

**7. Область развёртывания у погашенного гейта показывает то, что было отправлено.** Блокировка
переключателей (задача 3) фиксировала локальный выбор, а не отправленное значение: если пользователь
переключил область, а гейт погас не от клика по «Развернуть» (ответ свободным текстом, более новый
гейт), карточка навсегда оставалась с областью, которая никуда не отправлялась. `DeployConfirmation`
теперь запоминает область в момент клика по «Развернуть»; у погашенного гейта показывается именно она,
а если подтверждения отсюда не было — `targetScope` с бэкенда. Два новых теста в
`DeployConfirmation.test.js`.

⚠️ Второй остаточный пробел, требующий изменения на бэкенде: гейт межартефактной эскалации.
`ESCALATION_ACTIONS` (`AgentOrchestratorService.kt:371-376`) — это `CONFIRM` «Добавить поля и
продолжить» / `SKIP` / `ABORT`, и выставляет их только `presentEscalationApproval`. Если пользователь
вместо кнопки отвечает свободным текстом, классификатор сводит ответ к `QUESTION`, а ветка `QUESTION`
в `handleStepApprovalInternal` (строки 4692–4704) отдаёт `STEP_ERROR_ACTIONS` (`RETRY` / `SKIP` /
`ABORT`) — без `CONFIRM`. `state.pendingEscalation` при этом остаётся, и попасть в
`handleEscalationConfirm` можно по-прежнему только через `CONFIRM`. По позиционному правилу старая
карточка эскалации гаснет — то есть кнопки «Добавить поля и продолжить» на экране не остаётся вовсе;
`RETRY` не равнозначен, он сбрасывает `pendingEscalation` и просто перезапускает заблокированный шаг.
В `develop` старая кнопка оставалась активной, так что это ухудшение. Восстановиться можно только
свободным текстом («добавь поля и продолжи» классифицируется как `CONFIRM` — он входит в набор,
разрешённый для `WAITING_STEP_APPROVAL`), кнопки для этого нет.

Со стороны `ecos-ui` это не лечится: интерфейс не отличает `CONFIRM` эскалации от `CONFIRM` плана
(идентификаторы переиспользованы намеренно), а исключение из правила актуальности для набора
`[CONFIRM, SKIP, ABORT]` вернуло бы ровно тот дефект, ради которого правило и вводилось — после
ответа `pendingEscalation` сбрасывается, и клик по старой кнопке `CONFIRM` трактуется уже как `RETRY`,
то есть перезапускает шаг. Правильное место правки — `citeck-ai`: в ветке `QUESTION` отдавать
`ESCALATION_ACTIONS`, когда `state.pendingEscalation != null`. Отдельная задача.

**8. Ответ по файлу больше не гасит диалоговый гейт того же сообщения.** Обратная сторона правки 3.
`handlePendingFileSaveAction` (`AgentOrchestratorService.kt:754`) обрабатывается до маршрутизации
запроса к агенту: он сохраняет или отменяет один файл и возвращает системное сообщение без `actions`
и без `agentStatus`, а состояние агента (например `WAITING_PLAN_APPROVAL`) не меняется. Интерфейс
дописывал это сообщение в список, смешанный набор `[CONFIRM, REJECT, new_record|<ref>,
file_cancel|<ref>]` переставал быть последним, и `CONFIRM`, которого бэкенд всё ещё ждёт,
отрисовывался заблокированным — ответить на гейт можно было только свободным текстом. Ухудшением по
сравнению с `develop` это не является (там клик обнулял `actions` и кнопки просто исчезали), но
заявленной цели ветки — «живой гейт остаётся кликабельным» — противоречит напрямую, и комментарий в
`utils.js` утверждал ровно обратное тому, что происходило.

Решение: `handlePollingResult` помечает такой ответ признаком `isFileActionNotice` (он выставляется,
когда результат отвечает на файловое действие — `consumedTempRef` уже вычисляется там для вырезания
превью), а `isSupersededByNewerMessage` пропускает такие сообщения так же, как `isError`. Заодно
`agentStatus` при файловом ответе больше не сбрасывается в `null`: ответ по файлу ничего у агента не
спрашивал, и гашение индикатора утверждало бы, что агент перестал ждать. Четыре новых теста
(`utils.test.js` — три случая позиционного правила, `MessageList.test.js` — полный путь отрисовки,
`useUniversalChatHandlers.test.js` — признак на сообщении и сохранение `agentStatus`); мутацией
проверено, что без правки четыре из них падают.

**9. Отправленная область развёртывания переехала из состояния компонента на сообщение.** Правка 7
хранила её в `useState` самого `DeployConfirmation`, но список сообщений размонтируется при каждом
сворачивании окна чата (`AIAssistantChat.jsx:588`, `{!isMinimized && …}`). После разворачивания
`sentScope` терялся, и погашенная карточка снова показывала `targetScope` с бэкенда — то самое
«область, которая никуда не отправлялась», ради чего правка 7 и делалась. Теперь `DeployConfirmation`
передаёт выбранный вариант целиком (`deployScopeOption` — в нём есть локализованный `label`, которого
нет в теле запроса), а `handleActionClick` записывает его в `messageData.sentDeployScope` рядом с
`actionsResolved`; в тело запроса поле не попадает. Три новых/обновлённых теста в
`DeployConfirmation.test.js` (включая свежее монтирование карточки) и один в
`useUniversalChatHandlers.test.js`; мутацией проверено, что без записи признака тест падает.

Остаточно: локальный выбор в переключателе (`selectedKey`) при сворачивании по-прежнему сбрасывается
на `targetScope`. Для живого гейта это видно на экране (переключатель показывает вариант по
умолчанию), отправлено будет именно показанное значение, так что расхождения между показанным и
отправленным нет; поведение существовало и до этой ветки.

**10. Устаревание гейта передаётся отдельно от заморозки на время запроса.** `MessageList` отдавал
карточкам единственный признак `actionsDisabled = устарел || идёт запрос`. Для блокировки кнопок это
верно, но `DeployConfirmation` и `AgentPlanMessage` читали его ещё и как «решение по гейту принято» —
и решали по нему, что́ показывать. А `handleActionClick` поднимает заморозку **до** POST, а
`sentDeployScope` записывает только после его возврата. В итоге весь круг обмена карточка развёртывания
показывала область по умолчанию с бэкенда: подпись отпрыгивала от только что подтверждённой области,
а точка переключателя перескакивала на первый вариант — то самое «показана область, которая не
отправлялась», ради устранения которого делались правки 7 и 9. У карточки плана тем же образом на
время любого постороннего запроса пропадала подсказка живого гейта.

Решение: `MessageList` передаёт третий признак `actionsStale` — чистое устаревание, без заморозки.
Блокировка кнопок и переключателя по-прежнему идёт по `actionsDisabled` (заморозка исключений не
имеет), а вот содержимое карточек — по `actionsStale`. Три новых теста: сохранение выбранной области
на время запроса (`DeployConfirmation.test.js`), сохранение подсказки при заморозке
(`AgentPlanMessage.test.js` и сквозной через `MessageList.test.js`) и проброс признака отдельно от
заморозки в двух ветках `MessageItem`.

**11. Отменённый пользователем запрос больше не считается продвижением диалога.** `isSupersededByNewerMessage`
пропускал `isError` и `isFileActionNotice`, но не `isCancelled`. Отмена запроса переписывает сообщение
обработки в отменённое (`cancelRequest` / `handlePollingCancelled`), и оно остаётся в истории навсегда.
Клик по файловой кнопке — единственный способ начать запрос без пользовательского сообщения перед ним,
поэтому для смешанного набора это отменённое сообщение оказывалось единственным, что стоит между
гейтом и концом истории: `CONFIRM`/`REJECT` гасли навсегда, хотя `actionsResolved` никто не выставлял
и агент всё ещё ждал ответа. Отменённый ход — это ход, который не состоялся, ровно как и ошибка
отправки, поэтому он теперь тоже не перекрывает гейт. На остальные пути правка не влияет: свободный
текст перекрыт пользовательским сообщением, а клик по диалоговому действию — собственным
`actionsResolved`. Шесть новых тестов (`utils.test.js` — четыре случая правила, `MessageList.test.js` —
сквозная отрисовка смешанного набора и возврат к гашению после настоящего сообщения).

**12. Неудачная отправка свободного текста больше не гасит гейт.** `handleSubmit` дописывает
сообщение пользователя в историю **до** запроса, поэтому при сетевой ошибке в списке остаётся
сообщение о ходе, которого не было: по позиционному правилу оно перекрывало гейт, и кнопки гасли
навсегда, хотя агент по-прежнему ждал ответа. Получалась несогласованность — уведомление об ошибке
правило пропускало, а сообщение, которое это уведомление объясняет, нет. Ветка `catch` теперь
помечает своё сообщение признаком `isFailedSend`, и `isSupersededByNewerMessage` его пропускает — по
тому же правилу, что уже действует для `isError` и `isCancelled` («ход, которого не было, гейт не
перекрывает»). Ошибка опроса под правку сознательно не попадает: там запрос до бэкенда дошёл и мог
быть применён. Пять новых тестов: три случая правила в `utils.test.js` (неудачная отправка,
доставленный ответ, повтор после неудачи) и два в `useUniversalChatHandlers.test.js` (признак
выставляется при отказе и не выставляется при принятом запросе).

**13. Выбранная область развёртывания переживает сворачивание окна.** `sentDeployScope` (правка 10)
вынесла на сообщение уже **отправленную** область, но черновой выбор оставался в состоянии
`DeployConfirmation`, которое уничтожается тем же самым размонтированием: `AIAssistantChat` рендерит
список сообщений как `{!isMinimized && …}`. Пользователь переключал область на рабочее пространство,
сворачивал окно, разворачивал обратно — выбор молча возвращался к области бэкенда по умолчанию, и
следующее нажатие «Развернуть» отправляло глобальное развёртывание. Черновой ключ теперь тоже живёт
на сообщении (`messageData.draftDeployScopeKey`): `useUniversalChat.selectDeployScope` записывает его
по id сообщения, `AIAssistantChat` → `MessageList` → `MessageItem` пробрасывают обработчик,
`DeployConfirmation` инициализирует своё состояние из сообщения. Пять новых тестов:
`DeployConfirmation.test.js` (выбор сообщается наверх; после перемонтирования карточка показывает
черновик и отправляет именно его), `MessageList.test.js` (сквозной проброс с id нужного сообщения и
отрисовка черновика) и `useUniversalChatHandlers.test.js` (ключ пишется только адресованному
сообщению и перезаписывается при повторном выборе).

**Прочее по мелочи:**

- `.ai-assistant-chat__action-button--stale` перекрывался правилом `:disabled` из миксинов кнопок
  (специфичность класса против класса с псевдоклассом), поэтому `opacity: .45` не применялся. Селектор
  продублирован с `:disabled`.
- Проверка `if (disabled) return;` в обработчике клика удалена: браузер не доставляет событие клика
  на заблокированной кнопке ни при клике пользователя, ни при программном вызове `.click()`.
- `resolveResizeHandles` убрана — вместо неё два модульных списка в `AIAssistantChat.jsx`
  (`CORNER_RESIZE_HANDLE` / `NO_RESIZE_HANDLES`), заодно проп перестал получать новый массив на
  каждый рендер. Пояснение про `_excluded` осталось рядом с константами.
- Пробелы в тестах закрыты: проброс признаков через `MessageItem` во все четыре ветки (раньше удаление
  проброса не роняло ни одного теста), заблокированное состояние `DeployConfirmation` (включая
  переключатели области) и `BusinessAppMessage`, смешанный набор в `MessageActions`, а тест «гейт
  остаётся рабочим после отказа запроса» теперь проверяет само правило отрисовки, а не только
  внутренний признак `actionsResolved`.
- В `AGENTS.md` добавлены раздел про правила чата ассистента, рабочая команда запуска ESLint (со
  сноской про `DISABLE_V8_COMPILE_CACHE=1` на Node 22) и исправлен рецепт запуска одного теста —
  `yarn test` не завершается, нужен `yarn test:ci`.
