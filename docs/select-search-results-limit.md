# Select: при поиске показываются только 4 варианта (COREDEV-359)

В выпадающем списке (`EcosSelect` и штатный formio `select` — оба построены на choices.js) при вводе
текста оставалось не более четырёх совпадений, а высота списка не менялась: под четырьмя строками
оставалось пустое место от полного списка. Пользователь видел «полный» ответ поиска, который на
самом деле был обрезан.

## Воспроизведение

1. Журнал `ui-actions` (`/v2/journals?journalId=ui-actions&viewMode=table&ws=admin$workspace`),
   навести курсор на строку → «Edit Properties».
2. Поле «Action Type» (27 вариантов), открыть и ввести `o`.

Замеры до исправления (вьюпорт 1600×950):

| состояние | отрисовано | высота выпадашки | высота списка |
| --- | --- | --- | --- |
| открыт, без поиска | 27 | 362 px | 300 px |
| введено `o` | **4** | 362 px | 164 px |

То есть ~198 px пустоты под четырьмя строками, при том что подходящих вариантов 15 (`Download Card
Template`, `Content Preview Modal`, `Task Outcome` и остальные в список не попадали).

## Корневая причина

Дефекта два, и оба видны в одном кадре.

### 1. Ограничение на число отрисованных совпадений

`searchResultLimit` в choices.js 8.0.0 по умолчанию равен `4` и применяется только когда идёт поиск
(`_createChoicesFragment`):

```js
var choiceLimit = rendererableChoices.length;
if (this._isSearching) {
  choiceLimit = searchResultLimit;      // 4
} else if (renderChoiceLimit > 0 && !withinGroup) {
  choiceLimit = renderChoiceLimit;
}
for (var i = 0; i < choiceLimit; i += 1) { ... }
```

Без поиска рисуется весь список, с поиском — первые четыре по релевантности. Значения «все» у опции
нет: `-1` не нарисует ничего (цикл не выполнится), а большое число прокрутит цикл по пустым
индексам. Опция читается ровно в одном месте библиотеки — больше `searchResultLimit` ни на что не
влияет.

### 2. Замороженная высота выпадающего списка

`recalcDropdownPosition` (наш патч, ECOSUI-2736) при открытии проставлял
`style.minHeight = <текущая высота>`. Пока список полный, это ничего не меняет, но после фильтрации
коробка остаётся прежней высоты — то самое пустое место. Сбросить её было некому:
`hideDropdown` вызывал `style.removeProperty('minHeight')`, а `removeProperty` принимает
**CSS-имя** свойства (`min-height`), поэтому вызов ничего не делал.

## Исправление

Всё в общем модуле `src/forms/choices/index.js`, через который библиотеку импортируют оба
компонента, так что исправление распространяется и на `EcosSelect`, и на переопределённый
`select` formio.

1. `Choices.defaults.options.searchResultLimit = null` — «без ограничения», и патч
   `_createChoicesFragment`, который подставляет вместо `null` число найденных совпадений на время
   отрисовки. Лимит, переданный вызывающим кодом (в том числе через `customOptions` компонента),
   по-прежнему соблюдается.
2. `recalcDropdownPosition` больше не выставляет `minHeight` (и `hideDropdown` не пытается его
   снять) — высота коробки определяется списком, который в ней сейчас лежит.
3. `recalcDropdownPosition` выставляет `bottom: auto`. Это обязательное следствие пункта 2: стили
   choices.js раскрывающийся вверх список позиционируют по нижнему краю
   (`.is-flipped .choices__list--dropdown { top: auto; bottom: 100% }`), а наш патч ставит ещё и
   `top` — элемент оказывается зажат обоими краями, и его высота считается по ним, а не по
   содержимому. Пока высоту держал `min-height`, это было незаметно; без него выпадашка,
   раскрытая вверх, схлопывалась в 0 px и исчезала с экрана.
4. Направление раскрытия фиксируется на время сессии: `needToFlip` теперь учитывает
   `containerOuter.isFlipped`. Класс `is-flipped` контейнер снимает только при закрытии, поэтому
   без этого пересчёт после фильтрации мог поставить коробку вниз, оставив стили верхнего
   раскрытия.
5. Патч `_renderChoices`: пока список открыт, после каждой перерисовки вызывается
   `recalcDropdownPosition`. Позиция считалась один раз, при открытии, и якорем служит верхний край;
   у списка, раскрытого вверх, изменившаяся при фильтрации высота иначе отрывала бы его от поля.

Отдельного упоминания стоит `src/components/dashboard/widgets/Tasks/style.scss`: там уже был
локальный обход этой же проблемы (`.is-flipped .choices__list--dropdown { top: 100%; bottom: auto }`)
для виджета задач. Теперь он не нужен, но и не мешает — правило не трогали.

## Проверка

- `src/forms/choices/__tests__/searchResults.spec.js` — поиск отрисовывает столько вариантов,
  сколько нашёл (до исправления 4 из 8), полный список без поиска не меняется, явный
  `searchResultLimit` соблюдается, `min-height` на выпадашке не остаётся, открытый список
  переякоривается при перерисовке, закрытый — нет.
- Полный прогон `jest`: 222 сьюта / 2849 тестов — зелёные.
- Браузер, та же форма «Action Type» (1600×950): по `o` рисуется 15 совпадений вместо 4, список
  занимает свои 300 px со скроллом, `min-height` нет, отступ от поля прежний (6 px).
- Браузер, вьюпорт 1400×620, где список раскрывается вверх: 27 вариантов — 362 px, по `script`
  одно совпадение — 103 px, расстояние до поля неизменные 6 px (до исправления коробка оставалась
  362 px при одном совпадении).
- Проверка вне модального окна: два `Choices` смонтированы на пустой странице у верхнего и нижнего
  края (в дев-режиме патченный модуль доступен как `import('/src/forms/choices/index.js')`).
  Вниз: 344 px → 85 px при одном совпадении, край прижат к полю; вверх: то же, отступ 10 px не
  меняется.

## Замечания по инструментам

- Класс внутреннего контейнера у обоих компонентов переопределён на `form-control`, поэтому
  привычного `.choices__inner` в DOM нет — кликать надо `.formio-component-<key> .choices > .form-control`.
- В jsdom нельзя проверить `style.bottom = 'auto'`: `cssstyle` принимает для `bottom` только длины и
  молча отбрасывает `auto` (в браузере значение проставляется). Этот пункт закрыт только браузерной
  проверкой.
- Найти на стенде форму с длинным `select` проще всего запросом определений форм:
  `uiserv/form` → `definition?json`, и обойти дерево в поисках `data.values` длиннее четырёх.
