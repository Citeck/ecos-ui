# Виджет комментариев следует за записью своей вкладки (COREDEV-538)

## Проблема

В базе знаний переходы между статьями делаются деревом («Categories»). После клика по статье
содержимое справа меняется, а виджет «Comments» продолжает показывать комментарии **предыдущей**
статьи: список, счётчик в шапке и — главное — редактор нового комментария остаются привязаны к
прежней записи. Комментарий, написанный «под статьёй», уходит на ту статью, с которой пользователь
пришёл (в MM это описали как «комментарий цепляется ко всей базе»).

### Воспроизведение

1. `/v2/dashboard?ws=TEST2&recordRef=emodel/wiki@TEST2$ROOT` (на корне и на дочерней статье есть по
   одному комментарию).
2. Кликнуть дочернюю статью в дереве.

ФР: URL и статья — дочерние, в виджете — комментарий корня, новый запрос `emodel/comment` не уходит.
ОР: виджет показывает комментарии дочерней статьи.

## Корневая причина

Дерево (`ecos-ui-hierarchical-tree-widget-plugin`) переключает статью через
`updateCurrentUrl({ recordRef })` → `changeUrl(url, { updateUrl: true })` →
`PageService.changeUrlLink` → событие `CHANGE_URL_LINK_EVENT`. Сага `customEvent`
(`_handleChangeUrl`) для `updateUrl` делает только `replaceHistoryLink` и `updateTab({ updates })`.
**Страница при этом не перерисовывается**: `Layout.renderWidgets` берёт `record` из
`getSearchParams()` в момент рендера, а рендера нет — все виджеты остаются с `record`, с которым
смонтировались (проверено через React fiber: у `Comments` и `HierarchicalTreeWidget` после клика
`props.record` по-прежнему `…$ROOT`).

Виджеты дерева и публикации это переживают, потому что сами читают `getRecordRef()` в своём
обработчике `CHANGE_URL_LINK_EVENT`. `Comments.jsx` всё вяжет на `props.record`: селектор
`selectStateByRecordRef`, `fetchData` (только в `componentDidMount`), `renderEditor` →
`<Comment recordRef={record}>` → `createComment`. Его обработчик `handleChangeTabLink`
(COREDEV-445) сравнивает `getRecordRef() === record` — после перехода они различаются, и он молчит.

Смежное наблюдение: все wiki-страницы одного воркспейса делят **один ключ вкладки**
(`PageService.keyId` → `dashboard-wiki-<ws>`), поэтому обычная ссылка на статью не открывает новую
вкладку, а заменяет wiki-вкладку на месте — в этом пути Layout перерисовывается и виджет получает
новый `record` пропсом (без ремаунта).

## Исправление

`src/components/dashboard/widgets/Comments/Comments.jsx`:

- Дефолтный экспорт — обёртка `CommentsWidget` над connected `Comments`. Она слушает
  `CHANGE_URL_LINK_EVENT` и реагирует **только** на перезапись URL своей вкладки:
  `event.params.updateUrl` (событие без него — открытие/замена другой вкладки) и
  `PageTabList.isActiveTab(tabId)` (кэшированные вкладки остаются смонтированными и обязаны держать
  свою запись — сценарий COREDEV-445). Запись берётся из `event.params.link`
  (`getRecordRef(link)`), а не из `window.location`: сага-слушатель обновляет адрес раньше только
  в силу порядка регистрации. Смена `props.record` от Layout (замена wiki-вкладки на месте)
  подхватывается через `getDerivedStateFromProps`.
- Внутренний `Comments` рендерится с `key={record}`: новая запись — новый инстанс. Подписки
  `instanceRecord.events.*` и `_updateWatcher` из `BaseWidget` привязываются к записи при
  монтировании, «переехать» на другую запись у живого инстанса они не умеют. Открытый редактор
  при смене статьи закрывается вместе с инстансом — черновик принадлежал другой статье.
- Подписки на события записи и на `CHANGE_URL_LINK_EVENT` перенесены из конструктора в
  `componentDidMount`: инстанс, который React создал и отбросил (StrictMode), иначе продолжал
  слушать и слал запросы — в деве счётчик запросов рос с каждым переходом.
- `handleChangeTabLink` не дёргает `updateComments`, пока идёт загрузка (`fetchIsLoading`):
  Dashboard отвечает на каждую перезапись собственным `updateTabLink` с тем же адресом, и без
  этого на каждый переход уходило три запроса вместо одного.

## Проверка

- `src/components/dashboard/widgets/Comments/__tests__/CommentsFollowRecord.test.js`: переход по
  перезаписи своей вкладки (запрос за новой записью, список и редактор на новой записи), та же
  запись — без запроса, скрытая вкладка — не реагирует, событие без `updateUrl` — не реагирует,
  ссылка без записи — не реагирует, отписка при размонтировании, отсутствие повторной проверки
  списка во время первой загрузки. `CommentsTabs.test.js` (COREDEV-445) без изменений.
- Браузер (локальный стенд, ws `TEST2`): корень ↔ дочерняя статья через дерево и заголовок
  виджета дерева — список, счётчик и запись редактора следуют за статьёй; один запрос
  `emodel/comment` на переход в продовой сборке (два в деве из-за StrictMode). Две вкладки
  (карточка задачи + wiki): навигация по дереву в wiki-вкладке не трогает виджет скрытой вкладки,
  возврат на неё показывает её комментарии.
