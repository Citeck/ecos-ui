# Журнал: переход к записям группы применяет фильтр из чужой ветки OR (COREDEV-371)

## Проблема

При активном комплексном фильтре с OR-условием по тому же полю, по которому включена группировка,
переход к сгруппированным записям («стрелка» в строке группы) подставляет **не то** значение.

### Воспроизведение

1. Задать фильтр с OR-условием по одному полю, например «Статус содержит Доработка» **ИЛИ**
   «Статус содержит Подписание».
2. Включить группировку по полю «Статус».
3. Нажать стрелку перехода к записям группы «Доработка».

ФР: в настройках фильтра — **два одинаковых** условия «Статус содержит Подписание», записи показаны
только для «Подписание».

ОЖ: одно условие «Статус содержит Доработка», записи — этой группы.

Два дефекта в одном сценарии: значение берётся из неверной ветки OR и условие дублируется.

## Корневая причина

`sagaGoToJournalsPage` (`src/sagas/journals.ts`) собирал новый предикат так:

```ts
originFilter = JournalsConverter.optimizePredicate({ t: 'and', val: cleanPredicates });
filter = getFilterParam({ row, columns, groupBy, predicate: journalData.predicate }); // условие группы
filter = concat(filter, originFilter.val);                                            // + ветки OR
const predicateValue = ParserPredicate.setPredicateValue(get(params, 'predicates[0]'), filter);
```

Здесь две ошибки, и обе нужны, чтобы получить описанную картину:

1. `optimizePredicate` схлопывает обёртку `and` до самого фильтра, и `originFilter.val` — это
   **список веток OR активного фильтра**. Они уже есть в дереве, в которое идёт запись
   (`params.predicates[0]` = `journalSetting.predicate`), поэтому дописывать их в `filter` не нужно
   вовсе — это чистое дублирование.
2. `ParserPredicate.setPredicateValue` записывал значение **во все узлы дерева с таким же `att`**, а
   для массива применял элементы по очереди. Для фильтра
   `or(status~Доработка, status~Подписание)` и клика по «Доработка» получалось:

   | шаг | применяемое условие | состояние обеих веток |
   |-----|---------------------|-----------------------|
   | 1 | `status ~ Доработка` (строка группы) | Доработка, Доработка |
   | 2 | `status ~ Доработка` (ветка 1 фильтра) | Доработка, Доработка |
   | 3 | `status ~ Подписание` (ветка 2 фильтра) | **Подписание, Подписание** |

   Последнее применённое условие затирало значение группы во всех ветках — отсюда и чужое значение,
   и дубль.

## Исправление

Добавлен `ParserPredicate.getGroupedRowPredicate({ row, columns, groupBy, predicate })`
(`packages/records-predicates/src/ParserPredicate.ts`) — он строит предикат целиком, а не правит
значения в существующем дереве:

- поля группировки закрепляются значениями строки (`getRowPredicates`, как и раньше);
- из активного фильтра убирается всё, что заведомо выполняется для каждой записи группы;
- результат — `and(остаток фильтра, закреплённые условия)` в обёртке, которую разбирает
  `ParserPredicate.parse`.

Убирать условие можно только тогда, когда доказано, что оно истинно для группы. Таких случаев два:

- условие буквально совпадает с закреплённым;
- условие стоит в **конъюнктивной позиции** — его выполняют все записи, проходящие фильтр, а раз
  группа существует, оно верно и для её значения. Ветки многозначного `or` конъюнктивными не
  являются: там условие по полю группировки вполне может быть ложной веткой, поэтому они
  сохраняются.

Что получается на практике:

| активный фильтр | группировка по `status`, клик «Доработка» | результат |
|-----------------|------------------------------------------|-----------|
| `status~Доработка OR status~Подписание` | вся группа условий зависит только от `status` | `status~Доработка` |
| `status~Доработка AND author=Иванов` | лишнее условие по `status` убрано | `author=Иванов AND status~Доработка` |
| `status~Доработка OR author=Иванов` | ветка совпадает с закреплённым условием | `status~Доработка` |
| `(status~Доработка AND author=X) OR (status~Подписание AND author=Y)` | ветки не конъюнктивны — сохраняются | исходный фильтр `AND status~Доработка` |

Сопутствующие удаления: `ParserPredicate.setPredicateValue` (единственный вызов был здесь, а его
семантика «записать во все узлы с таким `att`» и есть источник дефекта) и `getFilterParam`
(`src/helpers/urls.js`) — тонкая обёртка над `getRowPredicates` без других потребителей.

## Проверка

- `packages/records-predicates/src/__tests__/getGroupedRowPredicate.test.ts` — 10 сценариев, включая
  оба дефекта задачи и случаи, где ветки OR обязаны сохраниться.
- Полный прогон `jest`: 222 сьюта / 2855 тестов — зелёные. `tsc --noEmit` — новых ошибок нет
  (сравнение с базой до изменений).
- Браузерная проверка на локальном стенде, журнал «Issues active sprint» (проект TEST2), фильтр
  «Приоритет содержит Medium ИЛИ Приоритет содержит High», группировка по приоритету, переход в
  группу «Medium»:
  - до исправления — два условия «Приоритет содержит **High**» и запись TEST2-2 (High);
  - после — одно условие «Приоритет содержит **Medium**» и запись TEST2-1 (Medium).

## Замечания по стенду

Проверять группировку на локальном стенде можно не в любом журнале:

- группировка по ассоциации (`sprint`) падает на бэкенде: `Can't convert class kotlin.Array to
  class kotlin.Long`; по `_type` — «Grouping by columns [_type] is not allowed». Работают `priority`
  и `_status`;
- в UI колонка попадает в список группировки по `column.groupable`, который по умолчанию считается
  как «тип **не** входит в `GROUPABLE_TYPES`» (`journalColumnsResolver.js`). Список хранит
  legacy-константы в нижнем регистре, а в конфигурациях журналов типы записаны заглавными, поэтому
  сравнение почти всегда промахивается и `TEXT`-колонки (например «Приоритет») группируемыми не
  считаются, пока `groupable: true` не задан явно. Это отдельный дефект, в задачу не входит;
- мутации `emodel/ept-issue` по ассоциациям требуют приложения `ecos-project-tracker`, которого на
  стенде нет (`App is not available`); обычные атрибуты (`priority`, `_status`) меняются нормально.
