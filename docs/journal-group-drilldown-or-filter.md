# Журнал: переход к записям группы применяет фильтр из чужой ветки OR (COREDEV-371)

## Проблема

При активном комплексном фильтре с OR-условием по тому же полю, по которому включена группировка,
переход к сгруппированным записям («стрелка» в строке группы) подставляет **не то** значение.

### Воспроизведение

1. Задать фильтр с OR-условием по одному полю, например «Статус содержит Доработка» **ИЛИ**
   «Статус содержит Подписание».
2. Включить группировку по полю «Статус».
3. Нажать стрелку перехода к записям группы «Доработка».

ФР: в настройках фильтра — **два одинаковых** условия «Статус содержит Подписание», записи показаны
только для «Подписание».

ОЖ: одно условие «Статус содержит Доработка», записи — этой группы.

Два дефекта в одном сценарии: значение берётся из неверной ветки OR и условие дублируется.

## Корневая причина

`sagaGoToJournalsPage` (`src/sagas/journals.ts`) собирал новый предикат так:

```ts
originFilter = JournalsConverter.optimizePredicate({ t: 'and', val: cleanPredicates });
filter = getFilterParam({ row, columns, groupBy, predicate: journalData.predicate }); // условие группы
filter = concat(filter, originFilter.val);                                            // + ветки OR
const predicateValue = ParserPredicate.setPredicateValue(get(params, 'predicates[0]'), filter);
```

Здесь две ошибки, и обе нужны, чтобы получить описанную картину:

1. `optimizePredicate` схлопывает обёртку `and` до самого фильтра, и `originFilter.val` — это
   **список веток OR активного фильтра**. Они уже есть в дереве, в которое идёт запись
   (`params.predicates[0]` = `journalSetting.predicate`), поэтому дописывать их в `filter` не нужно
   вовсе — это чистое дублирование.
2. `ParserPredicate.setPredicateValue` записывал значение **во все узлы дерева с таким же `att`**, а
   для массива применял элементы по очереди. Для фильтра
   `or(status~Доработка, status~Подписание)` и клика по «Доработка» получалось:

   | шаг | применяемое условие | состояние обеих веток |
   |-----|---------------------|-----------------------|
   | 1 | `status ~ Доработка` (строка группы) | Доработка, Доработка |
   | 2 | `status ~ Доработка` (ветка 1 фильтра) | Доработка, Доработка |
   | 3 | `status ~ Подписание` (ветка 2 фильтра) | **Подписание, Подписание** |

   Последнее применённое условие затирало значение группы во всех ветках — отсюда и чужое значение,
   и дубль.

## Исправление

Добавлен `ParserPredicate.getGroupedRowPredicate({ row, columns, groupBy, predicate })`
(`packages/records-predicates/src/ParserPredicate.ts`) — он строит предикат целиком, а не правит
значения в существующем дереве:

- поля группировки закрепляются значениями строки (`getRowPredicates`, как и раньше);
- из активного фильтра убирается всё, что заведомо выполняется для каждой записи группы;
- результат — `and(остаток фильтра, закреплённые условия)` в обёртке, которую разбирает
  `ParserPredicate.parse`.

Логика вынесена в `packages/records-predicates/src/groupedRowPredicate.ts` и работает в два шага.

**Шаг 1 — зачистка «как движок»** (`withoutIgnoredConditions`): из дерева убирается ровно то, что
`removeEmptyPredicates` убирает перед запросом — пустые условия и опустевшие контейнеры (в том
числе пустая группа внутри OR). Важно: пустое условие в OR именно **удаляется из списка**, как это
делает движок (`or(amount=5, пустое)` ≡ `amount=5`), а не считается «истинной веткой» — иначе оно
коротило бы весь OR и молча выбрасывало соседние настоящие условия, расширяя выборку. Упрощение
шага 2 идёт по дереву, которое движок реально вычисляет — по нему же считались и группы.

**Шаг 2 — упрощение по группе** (`withoutGroupConditions`): убирать условие можно только тогда,
когда доказано, что оно истинно для группы. Таких случаев два:

- условие **выполняется на закреплённом значении** (`holdsForPinned`): буквально совпадает с
  закреплённым, либо закреплённое равенство фиксирует атрибут, и условие на этом значении истинно —
  `eq` с тем же значением или `contains`, чьё значение входит в закреплённое подстрокой
  (регистронезависимо, как серверный `contains` по тексту);
- условие стоит в **конъюнктивной позиции** — его выполняют все записи, проходящие фильтр, а раз
  группа существует, оно верно и для её значения. Ветки многозначного `or` конъюнктивными не
  являются: там условие по полю группировки вполне может быть ложной веткой, поэтому они
  сохраняются.

Известное ограничение: конъюнктивное правило рассуждает «истинность условия по группируемому полю —
функция значения группы», что строго верно только для однозначных атрибутов. Для **многозначного**
группируемого атрибута (запись с `tags = [X, Y]` попадает в обе группы) конъюнкт `tags contains X`
при переходе в группу Y отбрасывается, хотя не каждая запись группы Y его выполняет — выдача может
оказаться шире счётчика группы. Достижимо только для колонки ссылочного/многозначного типа с явным
`groupable: true` (по умолчанию такие в группировку не попадают); принято как осознанный компромисс.

Что получается на практике:

| активный фильтр | группировка по `status`, клик «Доработка» | результат |
|-----------------|------------------------------------------|-----------|
| `status~Доработка OR status~Подписание` | вся группа условий зависит только от `status` | `status~Доработка` |
| `status~Доработка AND author=Иванов` | лишнее условие по `status` убрано | `author=Иванов AND status~Доработка` |
| `status~Доработка OR author=Иванов` | ветка совпадает с закреплённым условием | `status~Доработка` |
| `(status~Доработка AND author=X) OR (status~Подписание AND author=Y)` | ветки не конъюнктивны — сохраняются | исходный фильтр `AND status~Доработка` |

Сопутствующие удаления: `ParserPredicate.setPredicateValue` (единственный вызов был здесь, а его
семантика «записать во все узлы с таким `att`» и есть источник дефекта) и `getFilterParam`
(`src/helpers/urls.js`) — тонкая обёртка над `getRowPredicates` без других потребителей.

## Возврат: пустые критерии сохранённого фильтра ломают OR-ветку

После первого исправления задачу вернули: на enterprise с сохранённой настройкой «двойной фильтр»
(журнал договоров) переход в группу «Доработка» показывал **0 записей**, а в фильтре появлялось
«…или Статус содержит Подписание **и** Статус содержит Доработка».

Отличие сценария от исходного: фильтр создан из панели настроек, где группа условий содержит **все
критерии журнала с пустыми значениями**, из которых заполнен только статус:

```
or( or( and(_created ge '', _disp contains '', status~Доработка, …ещё 7 пустых), status~Подписание ) )
```

Вторая корневая причина — рассинхрон трактовки пустого условия:

- `withoutGroupConditions` считал пустое условие (`val: ''`) содержательным и сохранял его. После
  выбрасывания закреплённого `status~Доработка` первая ветка превращалась в `and(9 пустых)`;
- перед запросом `removeEmptyPredicates` (`JournalsConverter.cleanUpPredicate`) выбрасывает пустые
  условия и **удаляет опустевшую группу из её OR**. Вакуумно-истинная ветка `or(TRUE, status~Подписание)`
  молча превращалась в `or(status~Подписание)` — семантика «все записи» становилась «только Подписание»,
  и вместе с закреплённым `status~Доработка` запрос давал пусто.

Исправление: перед упрощением дерево зачищается ровно как перед запросом —
`withoutIgnoredConditions` (шаг 1 выше) удаляет пустые условия из их списка по общему с движком
правилу (`isIgnoredByQuery` в `utils.ts`, его же использует `removeEmptyPredicates`; операторы без
значения `empty`/`not-empty` пустыми не считаются). Ветка из одних пустых условий и закреплённого
статуса после зачистки состоит из одного закреплённого условия, доказывается `holdsForPinned`,
весь OR корректно уходит — остаётся только условие группы.

Проверка возврата: сьют `getGroupedRowPredicate.test.ts` дополнен блоком «a criteria group padded
with empty conditions»; полный `jest` — зелёный; `tsc`
без новых ошибок. Браузерная проверка на локальном стенде (журнал «Issues active sprint», TEST2,
фильтр из панели настроек: Priority=Medium в группе с пустыми критериями ИЛИ Priority=High,
группировка по Priority): до фикса клик по группе Medium — «No data available» и фильтр
«…или Priority=High и Priority=Medium» (точное репро возврата); после — запись TEST2-1 и один
критерий «Priority Contains Medium». Клик по группе High симметрично даёт TEST2-2 и «Priority
Contains High».

## Группа закрепляется равенством, а не «содержит»

`getRowPredicates` брал оператор закреплённого условия из активного фильтра (наследие
`setPredicateValue`, которому нужно было вписаться в существующее дерево), а без фильтра — из
`EQUAL_PREDICATES_MAP`, где для текстовых колонок тоже стоит `contains`. Группа же — это **точное
значение** атрибута: с `contains` клик по группе «Подписание» захватывал и записи «Подписание
контрагентом», потому что id одного статуса входит в id другого подстрокой.

Теперь закрепление идёт по `GROUP_VALUE_PREDICATES` — аудит всех типов карты:

| тип | было (`EQUAL_PREDICATES_MAP`) | стало | почему |
|-----|------|-------|--------|
| `text`, `options` | `contains` | `eq` | подстрочная ловушка |
| `mltext` | `contains` | `eq` | бэкенд (`DbRecordsQueryDao`) конвертирует `eq` по MLTEXT в поиск точного значения локали (`contains '"v"'` с JSON-кавычками); plain-`contains` — LIKE по хранимому JSON, та же подстрочная ловушка |
| `date`, `datetime` | `ge` | `eq` | `ge` захватывает всё на дату и позже; диапазонные значения (`$TODAY` и т.п.) бэкенд сам разворачивает в `ge/lt` |
| числа, `boolean`, `qname`, `noderef` | `eq` | `eq` | без изменений |
| `assoc`, `category`, `person`, `authority*` | `contains` | `contains` | для ссылочных типов это членство точного ref (join таблицы ассоциаций), подстрок нет |
| `content` | `not-empty` | `eq` | `not-empty` — вообще не закрепление (вернул бы все записи с контентом); `content` группируем по умолчанию из-за инвертированной семантики `GROUPABLE_TYPES` |
| неизвестный тип | — (условие терялось) | `eq` | закрепление не должно молча исчезать |

Правило удаления условий симметрично поумнело (`holdsForPinned`): условие фильтра *вычисляется* на
закреплённом значении, и доказанное уходит — фильтр группы схлопывается до одного условия «Статус
Равно …» во всех трёх случаях сценария задачи, наборы записей точные (клик по «Подписание» — только
103 записи группы, без 46 «контрагентских»). Вычисляются только **позитивные строковые операторы**:
`eq` (точно, без сведения регистра — серверный `eq` это `=`), `contains`/`starts`/`ends`
(регистронезависимо, как серверные LIKE-операторы). Они экзистенциальны — одного совпавшего
значения достаточно даже для многозначного атрибута. **Отрицания** (`not-eq`, `not-contains`, …)
универсальны: для многозначного атрибута закреплённое значение ничего не говорит об остальных —
поэтому они никогда не вычисляются и остаются в фильтре. При этом конъюнктивное правило (см. выше)
от оператора не зависит и корректно убирает в том числе отрицания: конъюнкт по группируемому полю
выполняют все записи, прошедшие фильтр, а группа существует. В `not(...)`-контейнеры обход не
спускается вовсе — внутри отрицания «истинность» ветки меняет смысл.

## Выживший OR показывается вложенной группой условий

Когда ни одна ветка фильтра не доказуема для группы (например, группа «Согласование» при фильтре
`Доработка или Подписание` по другому полю или без пересечения значений), остаток фильтра выживает,
и раньше отдавался плоско: «Доработка или Подписание и Согласование». Скобок в панели фильтрации
нет, поэтому читалось это как `Доработка or (Подписание and закреплённое)` — хотя сам предикат был
правильный.

Теперь `getGroupedRowPredicate` собирает результат в форму, которую панель настроек показывает
однозначно: обычные остаточные условия и закреплённые значения группы идут в главную группу, а
выживший многоветочный `or` — **вложенной группой условий** (та же структура, которую создаёт
кнопка «Добавить → Группу условий»: `or[ and[ or[main], or[остаток] ] ]`):

```
Статус  Равно  Согласование
и ┌ Статус  Содержит  Доработка
  │ или
  └ Статус  Содержит  Подписание
```

(В сценарии задачи клик по «Подписание контрагентом» после введения `holdsForPinned` до вложенной
группы уже не доходит — ветка `contains Подписание` доказывается подстрокой, и фильтр схлопывается
до одного условия. Вложенная группа остаётся для веток, которые доказать нельзя, — прежде всего для
OR-фильтров по другим атрибутам.)

Раскладка: элементы верхнего `and` остатка разбираются по одному — конечные условия в главную
группу (закреплённые — следом за ними), каждый `or` — отдельной группой. `ParserPredicate.parse`
превращает элементы верхнего `and` в группы UI, `reverse` собирает ту же структуру обратно
(round-trip покрыт тестом «the surviving OR becomes a nested condition group»).

Браузерная проверка вложенной группы (там же, фильтр Issue~TEST2 ИЛИ Issue~zzz, группировка по
Priority, переход в Medium): запись TEST2-1, в модалке — главная строка «Priority Contains Medium»
и вложенная группа «Issue Contains TEST2 или Issue Contains zzz» со связкой «и». Полный `jest` — зелёный.

## Замечания по стенду

Проверять группировку на локальном стенде можно не в любом журнале:

- группировка по ассоциации (`sprint`) падает на бэкенде: `Can't convert class kotlin.Array to
  class kotlin.Long`; по `_type` — «Grouping by columns [_type] is not allowed». Работают `priority`
  и `_status`;
- в UI колонка попадает в список группировки по `column.groupable`, который по умолчанию считается
  как «тип **не** входит в `GROUPABLE_TYPES`» (`journalColumnsResolver.js`). Список хранит
  legacy-константы в нижнем регистре, а в конфигурациях журналов типы записаны заглавными, поэтому
  сравнение почти всегда промахивается и `TEXT`-колонки (например «Приоритет») группируемыми не
  считаются, пока `groupable: true` не задан явно. Это отдельный дефект, в задачу не входит;
- мутации `emodel/ept-issue` по ассоциациям требуют приложения `ecos-project-tracker`, которого на
  стенде нет (`App is not available`); обычные атрибуты (`priority`, `_status`) меняются нормально.
