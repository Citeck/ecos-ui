# Tooltip: подсказка остаётся на экране после ухода курсора (COREDEV-356)

## Проблема

Тултипы вкладок (`page-tab__tabs-item-tooltip`) не исчезают после того, как курсор ушёл с вкладки.
На экране может одновременно висеть несколько «неактуальных» подсказок; иногда, наоборот, подсказка
перестаёт появляться при наведении. То же самое наблюдалось и для других тултипов (например,
«Перейти в конструктор» поверх открытого модального окна).

### Воспроизведение

Стабильных шагов у тестировщика не было, наиболее частый сценарий:

1. Открыть несколько вкладок ECOS.
2. Навести на вкладку, дождаться появления тултипа.
3. Перейти на другую вкладку, проводя курсором по соседним.
4. Тем же путём вернуться на вкладку из шага 2.

ФР: минимум одна «неактуальная» подсказка остаётся видимой. ОР: подсказка показывается только под
курсором.

Важно: воспроизводимость зависит от загруженности страницы. На быстром локальном стенде окно гонки
близко к нулю, поэтому вручную баг часто не ловится — гонка детерминированно воспроизводится тестом
`src/components/common/Tooltip/__tests__/Tooltip.test.js`.

## Корневая причина

Состояние тултипа хранится в `Tooltip.state.isOpen`, а `TooltipWrapper` управлял им **переключением**:

- `TooltipWrapper.show()` работал только `if (!this.props.isOpen)`, `hide()` — только `if (this.props.isOpen)`;
- оба вызывали `props.toggle(e)`, а `Tooltip.onToggle` делал `setState(state => ({ isOpen: !state.isOpen }))`.

`props.isOpen` отражает **уже применённое** React состояние. Обработчики же живут на таймерах
(`showWithDelay`/`hideWithDelay`, для вкладок задержка равна 0) и выполняются раньше, чем React
успевает применить предыдущий `setState` — на нагруженной странице между запросом изменения и его
применением проходит несколько задач планировщика.

Последовательность отказа:

1. `mouseover` → `show()`: `props.isOpen === false` → запрошено открытие (изменение ещё не применено).
2. Курсор уходит, `mouseout` → `hide()`: `props.isOpen` **всё ещё `false`** → условие не выполняется,
   скрытие **теряется**.
3. React применяет открытие. Больше событий по этой цели не будет — подсказка висит навсегда.

Зеркальный случай (возврат курсора до применения закрытия) приводил к тому, что подсказка не появлялась.
Так как состояние менялось «переключением», результат зависел от чётности числа вызовов, а не от
намерения — любой потерянный вызов защёлкивал тултип в неверном состоянии.

## Исправление

`src/components/common/Tooltip/TooltipWrapper.jsx`, `src/components/common/Tooltip/Tooltip.jsx`:

- `TooltipWrapper` запоминает **запрошенное** состояние (`this._requestedOpen`) и проверяет его вместо
  `props.isOpen`; поле пересинхронизируется в `componentDidUpdate`, когда `props.isOpen` меняется
  извне (контролируемый режим, например `DropdownOuter`);
- `toggle(e, nextOpen)` передаёт владельцу желаемое состояние, а `Tooltip.onToggle` при булевом
  `nextOpen` делает `setState({ isOpen: nextOpen })` вместо инверсии. Сигнатура обратно совместима:
  без второго аргумента поведение прежнее (инверсия).

## Проверка

- `src/components/common/Tooltip/__tests__/Tooltip.test.js` — три сценария, средний до исправления
  падал (подсказка оставалась в DOM), после — проходит.
- Полный прогон `jest`: 220 наборов тестов / 2831 тест — зелёные.
- Браузерная проверка на локальном дев-сервере: 640 итераций случайных наведений, быстрых проведений
  курсора по ленте вкладок и переключений вкладок со сторожем, который ловит открытый тултип без
  наведённой вкладки, — нарушений нет.

## Что осталось непроверенным

В комментарии к задаче тестировщик отметил, что «пропали кнопки-переключатели табов, если они не
вмещаются на страницу». Локально это **не воспроизвелось**: при реальном переполнении ленты (130 px)
стрелки появляются в том же кадре, что и переполнение. Нужны условия тестировщика (ширина окна,
число вкладок, восстанавливаются ли стрелки после изменения размера окна).
